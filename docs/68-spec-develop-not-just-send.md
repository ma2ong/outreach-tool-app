＃ 68 — 每天不只是发信，还要开发

## Allen 的原话

> 你现在总是在关注发送，每天的任务都只安排了发送任务，似乎没有客户开发的任务。……开发不仅仅是
> 要开发新客户，还要在开发的过程中如果有发现现有客户的新的信息……这才是一个严格的专业的
> 外贸业务员。

他说对了，而且这解释了前面那个"邮件计划为什么这么少"：**管道空了**。1313 家客户里 611 家
发过一次就再没下文，93 家从没发过，而每天新进来 5–10 家。发送端优化到极致，也发不出没有的
东西。

这份 spec 把四件事接到现有架构**之上**，不推翻任何东西。

## 一、关系事件流（追加，不取代）

一段关系现在被切在六张表里：`outreach`、`send_log`、`sequence_enrollments`、
`social_dm_queue`、`inbox_messages`、`activities`。客户对话页要现拼时间线，
[65 号 spec](65-spec-recipient-local-time.md) 那个"芝加哥的周四下午是 UTC 周五凌晨、消息
静默丢失"的 bug 也源于此——发送时刻是队列表的一个日期列，而不是事件自己的属性。

新增 `relationship_events`：一条关系上发生过的每一件事，一行一条。

| 字段 | 说明 |
|---|---|
| `lead_no` | 哪家 |
| `at` | 什么时候（UTC） |
| `kind` | 发信 / 收信 / 退信 / 发现新事实 / 阶段变化 / 任务完成 |
| `channel` | email / whatsapp / instagram / facebook / web |
| `summary` | 一句人话 |
| `detail_json` | 结构化细节 |
| `source` | 谁写的：agent / allen / import / discovery |

**现有的表全部保留，继续是权威数据。** 事件流是它们的汇合处，不是替代品——写事件失败绝不
能让发送失败。客户对话页从此读一张表，而不是拼六张。

## 二、事实变化驱动（追加到定时器之上）

我原本的说法是"盯官网变化"。Allen 的修正是对的：

> 大家的官网说实话都不怎么维护的，职位人物的变动一般也不会公布出来，所以事实变化其实没多少

真正会变的是别处：

| 看哪里 | 能发现什么 |
|---|---|
| Instagram / Facebook 的新帖 | 最近做了什么项目、参加了什么展会、在招什么人 |
| 联系人页、LinkedIn、署名 | 负责人换了、职位变了、新的直线电话或邮箱 |
| 案例页 / 作品集 | 最近的项目——这是最好的开场白来源 |

所以"变化"的观察对象从官网首页移到**社媒动态和联系人信息**。定时器仍然负责"去看看"，
事实变化负责"值不值得做点什么"。

## 三、话术是配置，也是实验

现在换一个角度要写 spec、改数据库、重新部署——今天做这件事花了一个下午。而它本质上是个
实验：这套开场白对租赁商有效吗？对韩国有效吗？

`send_log` 已经在记 campaign，但那是个自由文本，把**四个市场、五种客户类型、三个步骤**混在
一个"361 封 1 个回复"里。这个数字指导不了任何决定。

追加三件事：

1. 每封信记下**序列版本、客户类型、第几步、语言**
2. 同一批客户按版本分流，不是全量换新
3. 仪表盘上按维度拆开的回复率表

**不做自动淘汰。** 样本量在这个业务里天然很小（一个市场一个月几十封），让程序按 p 值自动
关掉一个角度，比让 Allen 自己看着表决定更容易出错。

## 四、每天要开发，不只是发

### R4.1 每日计划必须包含开发额度

日报现在只有"今天发了多少"。**加一行"今天开发了多少"**：新公司、新联系人、补全的信息。

开发做不动的时候（搜索没结果、抓取失败）要在日报里说明，和发送做不动时一样。

### R4.2 渠道不只有一个搜索引擎

现在只有 DuckDuckGo。要加的：

| 渠道 | 找什么 |
|---|---|
| Google / DuckDuckGo | 关键词命中的公司官网 |
| **Google 地图 / 本地商户** | 按城市找 AV、租赁、广告公司——地址电话齐全 |
| **Naver** | 韩国市场搜索引擎；Google 在韩国覆盖不足 |
| 行业博客、协会名录 | 会员名单就是同类公司的集合 |
| Instagram / Facebook | 同行的关注者、同类账号 |

一个渠道死了不影响其他渠道，每个渠道单独记成功率。

### R4.3 开发过程中发现的老客户信息，要回流

**这是 Allen 强调的重点，也是最容易被漏掉的一条。**

搜索一个新公司时，经常会撞见一家已经在库里的公司——它的新联系人、新电话、换了职位的负责人、
最近做的项目。现在这些信息被丢掉了，因为流程只问"这是不是一个新客户"。

改成：每一条抓到的事实，先问"这家在不在库里"。

- 不在 → 新客户
- 在 → **补充它**：新联系人入 `contacts`，新事实进事件流，最近的项目更新 `hook`

老客户的一条新事实，比一个陌生的新公司更值钱——因为已经建立过接触。

### R4.4 补充遵守既有的真实性规则

回流的信息照样受 [45 号 spec](45-spec-truthful-lead-facts.md) 约束：写不出出处的不写，
不覆盖 Allen 手填的字段，不猜。

## 落地顺序

1. **事件流 + 开发回流**（一、四）——先让"开发"这件事在系统里存在并留痕
2. **话术实验**（三）——有了记账才知道该改什么
3. **社媒事实观察**（二）——最重的一块，放最后

## 不做的事

- 不推翻 `leads`、`outreach`、`send_log` 中的任何一张
- 不因为有了事件流就停止写原表
- 不做自动关停话术的统计判断
