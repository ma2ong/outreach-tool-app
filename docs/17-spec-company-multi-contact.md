# Spec 17 — 公司与多联系人

> 状态：Implemented / Verified
> 日期：2026-08-04

## 1. 业务问题

LED 项目通常同时涉及老板/采购、技术、财务和现场负责人。当前一家公司只能存一套姓名、职位、邮箱、电话：

- 新联系人会覆盖旧联系人，历史关系丢失；
- 不知道谁是决策人、技术人、付款人；
- 次要联系人回复时可能无法归属客户；
- 发送时无法明确默认发给谁。

## 2. 设计原则

- `leads` 继续代表公司，不做高风险重命名。
- 新增 `contacts` 作为联系人主数据；一家公司可有多人。
- 每家公司最多一个“主要联系人”，现有 `leads.contact_name/email/phone/title/linkedin/email_status` 由主要联系人同步，保证旧发送、序列、导出和个性化继续工作。
- 次要联系人不会自动变成默认发送对象；业务员必须明确“设为主要”。

## 3. 数据模型

`contacts`

- 关联：`lead_no`
- 基本：`name`、`title`、`email`、`phone`、`linkedin`
- 采购角色：`decision_maker/influencer/technical/finance/other`
- 状态：`is_primary`、`email_status`
- 来源：`legacy/manual/reply/discovered`
- 备注：`note`
- 时间：`created_at/updated_at`

约束：同一联系人邮箱不重复；一家公司只有一个主要联系人（由服务层保证）。

## 4. 迁移与兼容

- 启动时把公司原有姓名/职位/邮箱/电话/LinkedIn 迁成主要联系人，重复启动不重复。
- 新导入或快速添加的公司若带邮箱/电话，立即创建主要联系人。
- 旧 API 修改联系人兼容字段时，更新或创建主要联系人。
- 主要联系人切换、修改或删除时，同步公司兼容字段。
- 客户合并时合并联系人；同邮箱联系人只保留一条并补齐字段。

## 5. 回复归属

- 邮件从任一联系人邮箱发来，都归属到对应公司，并把 `contact_id` 写入收件箱。
- 新邮箱从唯一匹配的公司域名发来真人回复时，自动新增为次要联系人，不擅自替换主要联系人。
- WhatsApp 从任一联系人电话发来，也可匹配对应公司。
- 同邮箱或同号码出现跨公司歧义时不猜测，避免把回复挂错客户。
- 收件箱显示联系人姓名；无法确定具体联系人时只显示公司。

## 6. API 与界面

- `GET /api/contacts?lead_no=`
- `POST /api/contacts`
- `PATCH /api/contacts/{id}`
- `POST /api/contacts/{id}/primary`
- `DELETE /api/contacts/{id}`

客户详情增加“联系人”区：

- 查看全部联系人、采购角色和主要联系人；
- 新建、编辑、删除联系人；
- 一键设为主要联系人；
- 联系方式不再散落在公司基本资料中。

## 7. 不做

- 不为每个联系人建立独立销售管道；商机仍属于公司。
- 不自动轮流向多个联系人群发；这会放大投诉和公司内重复触达风险。
- 不猜测采购角色；缺失时标为“其他/未确认”。

## 8. 验收

1. 联系人 CRUD、主要联系人唯一性和兼容字段同步测试通过。
2. 旧数据迁移可重复执行且无重复。
3. 次要联系人邮件/WhatsApp 回复能归属公司和联系人。
4. 客户合并、删除、体检不会留下或误删联系人。
5. 前端可完成联系人新增、编辑、设主要和删除。
6. 后端全量、前端构建、真实数据库迁移和浏览器冒烟通过。
