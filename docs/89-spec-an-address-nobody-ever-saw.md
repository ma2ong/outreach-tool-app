＃ 89 — 一个没人在官网上见过的邮箱

## 从「深度研究能不能用在找客户上」来的

Allen 拿来 FrontierAgent / AgentHarness ——「单任务最高可调度 150 个子 Agent」的
深度研究 agent。照着它最有价值的那一条「**最终结论是否可以核查**」查自己的，
先撞上的不是客户开发，是退信。

## 退信不是随机的，它按「这个邮箱是谁看见的」分层

收过信的 500 家，按 `email_source` 分组，退信用 `bounced_at` 这个真实结果算：

| 邮箱从哪来 | 家数 | 真实退信 | 退信率 |
|---|---|---|---|
| 官网联系页 `site.contact-page` | 82 | 4 | **4.9%** |
| 官网首页 `site.homepage` | 20 | 1 | 5.0% |
| 手工录入 `manual` | 8 | 2 | 25.0% |
| **没有出处** | **390** | **77** | **19.7%** |

**在官网上亲眼见过的邮箱，退信率是没出处的四分之一。**

## MX 校验挡不住这件事 —— 这是最要紧的一句

第一反应是「发之前先验一遍 MX」。查了，这条路是死的：

```
历史上退信的 77 家无出处邮箱，今天的 email_status 全部是 invalid
```

而这个 `invalid` 是 `replies.py:305` 在**收到退信之后**打上的标 ——
`email_status` 对已经退过的信是 100% 准确，对还没发的信毫无预测力。同一个 84 家
样本里 `valid` 和 `role` 的退信率都是 0.0%，那不是模型好，那是同义反复。

正面的证据在待发池里：

```
482 家无出处、还没发过信的客户 —— 其中 267 家 email_status = valid，215 家 = role
```

**它们全都通过了 MX。** 而历史上和它们同一类的邮箱，退信率是 19.7%。
DNS 能回答「这个域名收不收信」，回答不了「这个具体地址存不存在」。
能回答后一个问题的只有一件事：**有没有人在这家公司自己的页面上见过它。**

## R1：发信前，无出处的邮箱先回官网看一眼

待发池里 483 家无出处的客户，**358 家有官网可以回去抓**，125 家连官网都没有。

对有官网的：跑一次 `enrich`，读联系页和首页，然后按看见的结果分三种：

* **官网上就有这个地址** → 盖上 `site.contact-page` / `site.homepage`，照常发。
  这不是新数据，是把一条一直没写下来的出处补上。
* **官网上有别的地址，没有这一个** → 用官网上的那个替换，出处跟着写。
  一个猜出来的 `info@` 和联系页上印着的 `sales@` 冲突时，印出来的那个赢。
* **官网读不到，或者页面上一个邮箱都没有** → 出处仍然是空。

## R2：研究不挡信（Allen 09-03 定）

第一版这条写的是「出处是空的，不发」，实现成 `block_unsendable` 把第一封信停成
`blocked`。**这条被推翻了，理由是对的：**

> 你研究做你的研究，你研究的过程中有有效信息就获取入库，没有有效就不入库。
> 反正不要影响我发信息或邮件。

所以现在的规则是：**没有任何一封信因为说不出邮箱出处而少发。** `due_queue`、
`block_unsendable`、`never_touched` 三处一律不看 `email_source`。

研究照跑，产出只有一种形状 —— **把地址补对**：

* 官网上就是这个地址 → 盖上出处（这封信本来也要发，现在多了一条出处记录）
* 官网上是另一个地址 → **换掉**（这封信照发，只是发对了地方）
* 官网读不到 / 页面上没有邮箱 / 这家公司没有官网 → **什么都不写**，信照发

第三种不再生成任务。483 家生成 483 条「去补联系方式」，是 483 条没人会做的噪音，
而且那个地址本来也会发出去 —— 那条任务不改变任何事。

**19.7% 那个数字仍然成立，处理它的方式换了：** 不是把信扣下来等出处，
而是在信发出去之前尽量把地址换成官网上印着的那一个。降退信，不降发信量，
这两件事不必二选一 —— 第一版把它们绑在一起是我的错。

## R3：125 家连官网都没有的，跳过，不是拦下

它们没有官网可读，`enrich` 无从下手，所以这一轮研究对它们什么也做不了 ——
`recover` 直接返回 `no_website`，一个字段都不写。**它们照常发信。**

写下来是因为「做不了研究」最容易被顺手写成「所以别发」。这两件事没有关系。

## 这条规则不该做的事

**不回头动已经发过的 483 家。** 它们的退信已经发生了，重新分类不会把信收回来，
只会把 `email_status` 这一列搅浑 —— 而 `replies.py` 还依赖它跳过死地址。

**不因为出处是空就标 `do_not_contact`。** 出处空说的是「我不知道这个邮箱对不对」，
不是「这家公司不要联系」。两者混起来，一次抓取失败就会永久删掉一个真客户。

## 验收

1. 一家有官网、邮箱印在联系页上的客户，回抓之后 `email_source` 被写上。
2. 一家官网上写着**另一个**邮箱的客户，地址被替换，出处跟着写，旧地址不再被使用，
   **而且这家公司仍然在可发池子里** —— 研究的产出是发对地方，不是少发。
3. 一家官网读不到的客户：什么都不写，不写出处，也不生成任务。
4. 一家没有官网的客户：不尝试抓取，什么都不写。
5. 出处为空从不写 `do_not_contact`。
6. 已经发过信的客户不被这条规则改写任何字段。
7. **一家说不出出处的公司照常进 `due_queue`、照常留在 `never_touched`，
   `block_unsendable` 不因为出处停任何一条报名。** 这一条守的是「研究不挡信」。

## 没做的

* **给 483 家已发客户补出处。** 见上，收益是零，风险是搅乱 `email_status`。
* **第三方邮箱验证服务。** 会把客户名单送到外面去，而这里真正缺的信息
  （这个地址是不是印在他们自己网站上）本来就在他们的官网上，自己读就有。
* **因为出处不明而暂停发送。** 见 R2，这是 09-03 明确推翻的方向。
* **role 地址一律不发。** `info@` / `sales@` 在这门生意里是常态：
  官网联系页上的 55 个 role 地址真实退信 0 家。按 role 一刀切会砍掉一批好线索。
