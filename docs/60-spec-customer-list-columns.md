＃ 60 — 客户库看得出这是谁

韩国客户 303 家，列表上「客户类型」几乎全是 `—`，公司名全是英文，没有一列写着对接的是谁。
而这些信息**库里都有**：

| 字段 | 韩国 303 家里有值的 |
|---|---|
| `company_local`（韩文公司名） | 176 |
| `tags`（Allen 标的客户类型） | 176 |
| 主联系人姓名 + 职位 | 130 |
| `target_fit`（系统推断的类型） | **39** |

「客户类型」那一栏读的是 `target_fit`，而 `target_fit` 只有 39 条有值——**列是空的，不是因为
没标，是因为读错了字段。**

## R1 韩文公司名写在英文名下方

Allen 的原话：韩国公司**韩语为主，英文为辅**。但列表的排序、搜索、去重都建立在
`company_en` 上，把主次倒过来会牵动一整套东西，收益只是视觉。

所以位置上顺从他的习惯，结构上不动：英文名在上，本地名紧跟其下，小一号。看的时候韩文在
眼里，系统里 `company_en` 仍然是主键那一列。

两个名字一样时只显示一个——`RGB Korea / RGB코리아` 这种小满里就混写在一起的值，重复显示
只是噪音。

## R2 「客户类型」显示 Allen 标的，系统推断的排后面

他自己标的类型是判断，系统推断的是猜测。判断在前。

- `tags` 里有客户类型 → 显示它
- 没有 → 显示 `target_fit`（如「租赁公司 (90)」）
- 都没有 → `—`

### R2.1 `tags` 是个混合袋，得分开

现在 `tags` 里同时装着两种东西：

- Allen 标的客户类型：`工程商`、`租赁客户`、`批发商`、`广告商`、`透明屏`
- 机器写的标记：`icp:signage`

带 `icp:` 前缀的不是客户类型，是分类器的中间产物，不该出现在「客户类型」这一栏。判据用
前缀，不用猜词。

## R3 客户类型是选出来的，不是打出来的

现在的标签框是自由文本，逗号分隔。自由文本的代价是**同一个类型会长出好几种写法**——
`工程商`、`工程商 `、`工程 商`，然后筛选就再也筛不干净。

选项来自小满那份已经用了多年的分类，因为那是他真实在用的语言，不是我们新发明的一套：

| 类型 | 小满里的数量 |
|---|---|
| 工程商 | 200 |
| 租赁客户 | 59 |
| 批发商 | 12 |
| 广告商 | 3 |
| 透明屏 | 2 |

一家公司可以同时是工程商和租赁客户（小满里有 13 家是），所以是多选，不是单选。

**不锁死**：允许填一个清单外的类型，新填的会出现在之后的选项里。锁死会逼着他在别的字段里
凑合记，那比不规范更糟。

## R4 加一列「客户名称」

写对接人，`김종수 대표`、`Thomas Yoo / International Sales` 这种。

一家公司登记了多位联系人时，只显示 `contacts.is_primary` 那位——这个标记已经存在，不用新
定规则。没有主联系人标记的，退回 `leads.contact_name`。

**名字里的东西原样显示。** `전완기_已回复` 这种是 Allen 自己在小满里手打的批注，看着不整齐，
但那是他的笔迹，不是脏数据，系统不去替他"清理"。

## 不做的事

- 不改排序、搜索、导出的主字段（仍然是 `company_en`）
- 不给没有韩文名的公司翻译一个出来（[45 号 spec](45-spec-truthful-lead-facts.md)：编不出出处的不写）
- 不自动把 `target_fit` 转成客户类型标签——推断和判断不混为一谈

## 验收

1. 韩国客户列表里，英文名下方有韩文名；两名相同的只显示一个
2. 标了「工程商」的客户，客户类型那一栏显示「工程商」而不是 `—`
3. `icp:signage` 不出现在客户类型栏
4. 客户类型是可勾选的清单，且能填清单外的新类型
5. 有主联系人的客户，列表上能看到名字和职位
