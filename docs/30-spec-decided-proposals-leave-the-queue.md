# Spec 30 — 点过确认的提议要离开待确认队列

**Status:** implemented and verified
**Date:** 2026-08-20
**Depends on:** Spec 24（提议与执行）

## 问题

Allen 点了「确认」，卡片留在「待确认」标签里不走，他以为没点上，再点一次，
得到一行红字：`提议已是 executed，不能重复确认`。

现场记录（提议 #8，韩国找客）：

- 10:12:36 点确认，后端开始同步执行
- 10:15:44 执行完成，数据库状态已是 `executed`
- 界面仍停在执行途中的快照（`progress.status = "searching"`，第 1/4 个关键词）

两个原因叠加：

1. `discover_run` 在 HTTP 请求里同步跑完，这次花了 3 分 08 秒。经 cloudflared
   隧道访问时请求会先被掐断（隧道有约 100 秒上限），本机直连则是长时间空等。
2. 前端 `act()` 只在成功分支刷新列表，`catch` 分支不刷新。请求一旦超时或报错，
   列表就永远停在点击前的样子——而后端其实已经把事情做完了。

于是「已经做完的事」和「还没点的事」在界面上长得一模一样。

## 规则

### R1 做过决定的提议，无论请求结果如何都要离开队列

`act()` 在 `finally` 中刷新列表。请求成功、失败、超时都要重新拉取真实状态：
界面显示的必须是数据库里的事实，而不是点击前的记忆。

### R2 「已经执行过」不是错误

后端 `提议已是 {status}，不能重复确认` 表达的是「这件事已经完成」，不是操作失败。
前端识别这类冲突，不显示红色错误，只刷新列表让卡片消失。

对 Allen 来说，他想要的结果（这件事被处理掉）已经达成了。把达成的结果报成错误，
只会让他怀疑是不是又出了问题。

### R3 正在执行的提议要显示在执行

`discover_run` 会把 `payload.progress` 实时写进数据库（`searching` / `enriching` /
`complete`）。当一条待确认提议已经有未完成的 progress 时，说明它正在跑：按钮显示
执行进度并禁用，而不是继续显示可点击的「确认」。

这条直接针对「我以为还没点击」——界面必须让人看出动作已经在进行中。

## 不做什么

- 不在本 spec 内把 `discover_run` 改成异步 job。同步执行长任务是更深的一层问题
  （它同时导致隧道超时），值得单独一个 spec 和一次完整改造；本 spec 先让界面不再
  骗人。
