＃ 120 — 删了一半，却报「删除失败」

## 2026-09-10 那次 500

Allen 在客户库勾了一批客户点删除，界面弹出「删除失败：Error: bulk delete 500」。
服务器日志里是这一行：

```
File "app/api/leads.py", line 199, in bulk_delete
    repo.delete_lead(conn, no)
sqlite3.OperationalError: database is locked
```

同一时刻后台的邮箱验证任务正在写库，写锁等满 30 秒仍没拿到（`DB_BUSY_TIMEOUT_MS`）。

**但那批客户里，排在出错那条前面的已经删掉了，而且已经提交。** 单条删除是原子的
（连接一关，没提交的部分回滚），所以库里没有半删的孤儿数据——问题全在他看到的那句话上：
界面说「失败」，实际删了 5 家。他唯一能做的是再点一次，而对已经删掉的那 5 家，
再点一次什么也补不回来。

**一个批量操作的部分成功，不是失败。把它报成失败，就是让人对着一个自己看不见的状态做决定。**

## R1 一条锁不住，不能拖累整批

`bulk_delete` 逐条捕获 `sqlite3.OperationalError`：这一条跳过、记下编号，循环继续。
其余的照删。

只捕获锁这一类错误。其它异常（外键、代码写错）仍然抛出去——那些是 bug，
把 bug 悄悄记成「这条没删成」，下次就更难发现。

## R2 返回值要说清楚删了几条、剩几条、为什么

```json
{"deleted": 5, "blocked_domains": [], "failed": [128, 1096]}
```

`failed` 是编号，不是布尔量。界面据此说人话：
**「已删除 5 家；2 家因数据库正忙没删掉，稍后再点一次删除即可」**——
[AGENTS.md 的交互原则](../AGENTS.md)：反馈要引导下一步，不能只报告问题。

三个调用点（客户库批量删除、体检逐条挑选删除、智能清理）都得说同一句话，
因为它们背后是同一个接口。

## R3 没删成的，不进「永不再收录」

勾了「同时加入永不再收录」时，域名是在删除**之前**写进黑名单的。
如果这条最终没删成，黑名单里就多了一条它的记录，而客户还在库里——
下次采集会把这家挡掉，而 Allen 以为自己什么都没做成。

所以顺序反过来：**先删，删成了再拉黑。** 一条记录要么两件事都发生，要么一件都不发生。
