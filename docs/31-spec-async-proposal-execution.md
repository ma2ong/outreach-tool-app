# Spec 31 — 执行离开 HTTP 请求

**Status:** implemented and verified
**Date:** 2026-08-20
**Depends on:** Spec 24（提议与执行）、Spec 30（界面不再撒谎）

## 问题

确认一条提议时，执行在 HTTP 请求里同步跑完。`discover_run` 要搜多个关键词、逐个抓
落地页，实测一次 3 分 08 秒。经 cloudflared 隧道访问时请求在约 100 秒被掐断，本机
直连则是长时间空等。

Spec 30 让界面在超时后仍能拉回真实状态，那是兜底，不是解法：请求本来就不该等一个
三分钟的任务。同步执行还带来第二个问题——两次点击如果同时进来，都会读到
`pending` 并各执行一次。

## 设计

`approve()` 内部本来就分两段：先把状态改成 `approved`／`edited_approved`，再执行。
同步执行让这个中间状态一闪而过。把它变成一个真实存在的阶段，就同时解决了等待和
并发：

- `mark_approved()`：校验 + 落状态 + 记录被编辑的 payload。快，留在 HTTP 请求里。
- `execute_approved()`：真正干活。交给后台任务。
- `approve()`：两者相连，语义不变，供 `auto` 自主执行路径和测试使用。

不引入新状态。`approved` 就是「已批准、正在执行」。

## 规则

### R1 确认请求立刻返回

`POST /proposals/{id}/approve` 标记状态后立刻返回 `{job_id, proposal}`，执行在后台
进行。`GET /proposals/job/{job_id}` 查执行结果，与 `/run` 的既有约定一致。

### R2 一条提议只会被执行一次

`mark_approved` 只接受 `pending`。第二次点击时状态已是 `approved`，被拒绝——并发
保护不再依赖执行有多快。

### R3 执行中的提议留在待确认页，但不可再点

待确认列表同时返回 `pending` 与执行中的提议。执行中的显示实时进度、按钮禁用。

理由：执行完就消失是对的，但三分钟里什么都看不到是另一种「点了没反应」。Allen
需要看见事情在推进，而不是看见一片空白然后猜。

### R4 进程重启不留幽灵

服务启动时，把仍停在 `approved`／`edited_approved` 的提议标记为 `failed`，
写明「服务重启，执行中断」。

后台任务活在进程里，进程没了任务就没了。不清理的话这些提议会永远显示「执行中」，
既不完成也不失败。标记失败而不是自动重跑：重跑一个可能已经发出过邮件的动作，
比让 Allen 看到失败再决定更危险。

## 不做什么

- 不改 `auto` 自主执行路径。它跑在 Agent 的后台循环里，本来就不占 HTTP 请求。
- 不做任务队列或持久化 job。内存 job 表配合 R4 的启动清理已经够用；
  真正的状态在 `agent_proposals.status` 里，job 只是这一次页面等待的凭据。
