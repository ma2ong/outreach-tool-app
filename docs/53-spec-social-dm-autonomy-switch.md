# 53 — 社媒私信的自动挡：默认半自动，全自动是 Allen 显式选的

## 这份 spec 要改一条铁律，所以它先说清楚在改什么

`AGENTS.md` 原文：

> Never auto-start a new WhatsApp/Instagram/Facebook conversation. Platform risk stays
> behind the existing manual cold-DM workflow.

Allen 要全自动。按 `AGENTS.md` 自己写的那条「被拦下时不许绕道」——**一道挡路的闸门要么
是错的（在 spec 里公开改规则），要么是对的（去做它要求的工作）**——所以这里公开改规则，
而不是找一条绕过它的路径。

改成：

> 默认不自动发起社媒对话。Allen 可以为某个渠道显式打开自动挡，打开时必须看到风险说明并
> 亲手确认；打开后仍受更严格的拟人化约束，且随时可以关。

**没有改的部分**：风险本身。Instagram 被封就是没了，WhatsApp 那个号绑着微信和全部客户
联系方式。`channel_outreach.py` 顶上那条 `exceeding ~20 got the WhatsApp account
rate-limited (2026-05-15)` 仍然是真事。改的只是"谁来决定承担它"——从"代码替 Allen
决定不承担"，变成"Allen 自己按渠道决定，并且看得见代价"。

## 规则

### R1 三挡，按渠道分别设

| 挡位 | 行为 |
|---|---|
| `off` | 连队列都不备（这个渠道当天完全静默） |
| `manual`（默认） | Agent 备好队列，等 Allen 按发送 |
| `auto` | Agent 到点自己发 |

按渠道而不是一个总开关：WhatsApp 那个号和 Instagram 账号的代价不一样，Allen 完全可能
愿意让 Instagram 自动跑而 WhatsApp 手动确认。

默认全部是 `manual`。**升到 `auto` 必须是一次显式的写操作**，不能由任何迁移、种子或
默认值带上去。

### R2 打开自动挡时，代价要写在按钮旁边

不是一句"确定吗"。打开 `auto` 的接口必须收到这个渠道的名字作为确认字符串——照抄一遍
才能打开——并且界面上写明这个渠道被封意味着什么。

理由和 [45 号 spec](45-spec-truthful-lead-facts.md) 一致：**系统不该替人做他没意识到
自己在做的决定**。

### R3 自动挡的节奏比手动更保守，不是更激进

打开自动不等于放开量。`auto` 沿用 [52 号 spec](52-spec-social-dm-daily-queue.md) 的
每渠道 8–15 条随机、周末减半、一家公司一天一个渠道，另外加两条只在自动挡才有意义的：

- **发送时刻每天随机**，落在 9:00–18:00 之间的某个点，不是每天同一分钟。定点执行是
  最好认的机器人特征之一，而手动挡天然没有这个问题——人不会每天 9:00:00 点发送。
- **一天只跑一次**。跑完就结束，不补、不追赶积压。落下的明天再说。

### R4 自动发出去的每一条，事后都要能看见

`auto` 发送后写一条运行记录：几点跑的、每个渠道发了几条、失败几条。和
[48 号 spec](48-spec-outbound-guards-and-quiet-agent.md) R3 的安静原则一致——没有值得
说的就不制造噪音，但**发生了发送就一定留痕**，因为那是花掉了账号风险的操作。

### R5 关掉必须立刻生效

关掉自动挡不需要重启、不需要等下一个周期。正在跑的那一批不强行中断（中途掐断浏览器会
留下半截对话），但下一个周期不会再启动。

### R6 自动挡不改变闸门

`message_guard`、do-not-contact、日上限、同日不重复、一家公司一渠道——全部照旧。自动
挡改的只是"谁按下发送"，不是"发什么"和"发给谁"。

## 验证

- `tests/test_social_autonomy.py`：默认是 `manual`；升到 `auto` 缺少确认字符串会被拒；
  `off` 的渠道连队列都不备；`auto` 的发送时刻每天不同且落在窗口内；一天只跑一次；
  关掉后下一个周期不发；自动发送留下运行记录。
- `manual` 挡下，任何自动路径都不得发送——52 号 spec 的那条测试继续有效。
