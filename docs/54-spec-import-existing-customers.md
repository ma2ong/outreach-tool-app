＃ 54 — 导入已经开发过的客户

## 一条规则决定了这个功能的全部难点

Allen 的小满 CRM 里有多年积累的客户：谈过的、报过价的、成交过的、聊崩了的。把它们搬进来
是有价值的——但**搬错一步比不搬更糟**。

系统现在每天自动给"未触达"的客户发第一封冷邮件。那封信的第一句是
`Saw the rental work you do around Houston.` 后面跟着"我们是做 LED 屏的，有项目可以找我"。

**把一个 2023 年就聊过报价的老客户导入成"未触达"，明天早上他就会收到这封信。**

对方读到的是：这家供应商完全不记得我是谁。这比从没联系过还糟——从没联系过只是陌生，
而这个是把已有的关系一笔勾销。

所以这份 spec 的核心不是"怎么读 Excel"，是**怎么保证不发生上面那件事**。

## 规则

### R1 导入的客户默认是「已触达」，不是「未触达」

除非文件里明确写着"从未联系过"，否则一律按已触达入库。

方向是刻意选的：把老客户误标成未触达，代价是一封让人反感的信和一段关系；把从没联系过的
误标成已触达，代价只是他暂时不进冷邮件队列——而他本来就在库外躺着，晚几天没有损失。
**两个方向的错不对等，所以往安全那边错。**

文件里如果有最后联系日期，用它；没有的话用导入日期，并在备注里写明"日期未知，按导入日
计"——[45 号 spec](45-spec-truthful-lead-facts.md) 的老规矩，写不出出处的事实不能装作
知道。

### R2 已经在库里的客户，只补空字段，不覆盖

导入的记录和现有记录冲突时（同邮箱、同网站、同公司名），现有的赢。小满里的信息可能是三年
前的，而库里的可能是上个月刚从官网读的。

只有一种情况会写入：**这个字段现在是空的**。补一个空邮箱是收获，覆盖一个刚验证过的邮箱是
损失。

### R3 列名要认，认不出要问，不能猜

小满的导出字段是勾选式的，列名取决于导出时选了什么，中英文都可能。所以：

1. 识别常见列名（中英文），映射到系统字段
2. **导入前先出一份映射预览**：每一列被认成了什么、认不出的有哪些、会新建多少家、会补多少
   家、会跳过多少家
3. 确认之后才写库

认不出的列不猜，原样丢进 `business` 备注字段——信息留着，但不会被当成结构化数据参与判断。

### R4 关系状态要落进 outreach，不是只写个标记

一个"已触达"的客户，`outreach` 里要有对应渠道的记录，因为发送资格、跟进序列、日报统计
读的都是那张表。只在 `leads` 上写个 stage 是不够的——那样序列照样会把他捞进去。

### R5 成交过和聊崩了的要区分出来

如果文件里有状态列（成交/丢单/黑名单之类），成交客户标 `won`，丢单标 `lost`，
明确拒绝过的直接 `do_not_contact=1`。

这几类客户的价值恰恰最高，但**对待方式和陌生客户完全相反**：成交过的应该聊复购，不是
自我介绍。

## 验证

- `tests/test_import_customers.py`：不带日期的导入一律标为已触达；已有客户的非空字段不被
  覆盖、空字段被补上；中英文列名都能认；认不出的列不丢失但也不参与结构化判断；成交/丢单/
  拒绝三种状态分别落到正确的位置；导入的客户不会出现在当天的冷邮件队列里。
