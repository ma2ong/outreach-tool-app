＃ 122 — 他写了六次「不要再发冷邮件」，一次也没生效

## 记忆是散文，发信看的是规则

库里 Allen 亲手写的记忆一共 8 条，其中 6 条在说同一件事：

> 与客户建立联系了，后续不发冷邮件信息（#182）
> 跟客户有在联系，偶尔有让我报价，但是还没成交。不用发冷消息了，先办法让对方成交（#172）
> 成交客户，但是2年多没下单了，想办法让客户下单。后续不发冷邮件或者信息（#306）

`lead_memory_items` 里的文字进的是 `draft.py` 和 `followup_decision.py` 的提示词——
它影响信怎么写，不影响信发不发。**发不发由 [recontact.BLOCKED_SQL](../backend/app/recontact.py)
说了算，那段 SQL 从来不读记忆。**

#306 和 #1306 侥幸安全，因为它们的阶段是 `won`，而 `won` 本来就被永久排除。
#182、#191、#172 只是还在 14 天冷却期里：到 2026-09-22、09-18、09-18，
它们会各自重新排进冷启动队列——尽管这三家已经分别被冷邮件触达 5 次、3 次、5 次，
尽管 Allen 已经写下了「不要再发」。

**一个系统里，人写下的指令必须和系统自己的规则在同一张桌子上。**
只能被 LLM 读到的指令，等于没有指令。

## R1 「停冷发」是一个字段，不是一句话

`leads.no_cold_outreach`：不再对这家发任何冷启动开发信和冷私信。

它和 `do_not_contact` 是两件事，差别正是 Allen 那句话的后半句——**「想办法让对方再次下单」**：

| | 冷邮件 / 冷私信 | 跟进任务、报价、手动发信、回信 |
|---|---|---|
| `do_not_contact` | 停 | 停 |
| `no_cold_outreach` | 停 | **照常** |

同行、竞争对手用前者；成交过的老客户、已经在聊的人用后者。
把老客户塞进 `do_not_contact` 会连复购的路一起堵死，那不是他要的。

## R2 三条冷启动路径，只改它们共同的那一处

邮件（`outreach.eligible_leads`）、社媒私信（`channel_outreach._targets`）、
每日社媒队列（`social_queue`）三条路都经过 `recontact.BLOCKED_SQL`。
所以规则加在那一段 SQL 里，不加在三个调用点上——
[recontact.py 开头那句话](../backend/app/recontact.py)已经说过它只拥有一个判断：
**这家公司现在还能不能被冷启动碰。** 这正是同一个判断。

注意 `BLOCKED_SQL` 现在从 `outreach` 表出发，只看得见发过信的公司。
停冷发必须对**从没发过信**的公司同样成立，所以它是 `UNION` 上去的一整个 `leads` 子查询，
不是加在原来那串 `AND` 后面。

## R3 常写的那几句话变成按钮，点一下同时改记忆和状态

他的 6 条手写记忆归成 5 种情形。每种是一个预设：一句写进记忆的话，加一个真实动作。

| 预设 | 动作 |
|---|---|
| 成交客户，很久没下单了 | 停冷发 + 阶段推进到「已成交」 |
| 已经建立联系了 | 停冷发 |
| 报过价，还没成交 | 停冷发 |
| 同行 / 竞争对手 | 标为不再联系 |
| 实际决策人另有其人 | 只写记忆 |

**预设的定义住在后端**（`app/agent/memory_presets.py`），前端只负责把它们画成按钮。
一句话要同时是记忆、是状态、还要将来能筛选，它就不能有两份定义。

## R4 点了预设，界面要说出它改了什么

「已停冷发」不是一条静默的数据库更新。写进记忆的那句话本身就是给人看的记录，
侧栏还要显示这家现在的状态——**一个看不见的开关，下次就没人敢信它。**
