＃ 95 — 两个信箱，一封信

## Allen 的两条（09-03）

> 首先 info 邮箱不要替换掉，你找到其他的邮箱的话，就当做一个新的渠道，而不是把原来的
> info 给替换掉。因为我们也不知道他哪个邮箱是真实的负责人只能都发。
>
> info 邮箱发信时可以不用发称呼，只有当确定对方的名称时才称呼，不确定的情况下情愿不发。

## 查下来的实情：能动的不是 193 家，是 7 家

503 家收过信的公司里 193 家用的是 `info@` / `sales@` 这类前台信箱，全库 412 家。
`decision_maker_radar` 已经跑过 **545 次扫描**，产出 270 个候选人：

| | |
|---|---|
| 有邮箱的候选人 | 24 → 全部已提升 |
| 没邮箱的候选人 | 246 → 全部卡在 `new` |
| 412 家 role 信箱公司里库里没人名的 | 393 家 |
| **候选人邮箱 ≠ 现在在用的地址** | **7 家** |

所以「给 193 家找具名联系人」今天真正能落地的是 7 家。其余卡在三处：
`MAX_SWEEP_ACCOUNTS = 2`（每轮只扫两家）、扫描队列面向有销售动作的客户
（冷的 info@ 客户进不去）、以及下面这条。

## 抓回来的名字是脏的

正则在页面上找「职位行附近最近的一行大写文字」，抓回来的有：

```
Nationwide Delivery | project manager      ← 服务名
Great Park Live     | Technical Director   ← 场馆名
Outside Sales       | production manager   ← 部门名
Markdown Content    | founder              ← jina 的排版残渣
```

收紧正则试了两轮，两头都不准：`Bart McCollum`、`TOM WILSON` 这种真人被误挡，
`Air Sanitizer` 照样放过。这就是 Allen 那句「不确定的情况下情愿不发」的落点。

## R1：第二个信箱抄送在同一封信里，不另发一封

`leads.email` 一个字不动。找到的具名地址进 `contacts`，发信时作为**同一封信**的
抄送人。

不另起一封，理由是收件方看到的东西：同一家公司收到两封几乎一样的冷邮件，比只收到
一封更像群发，而这套系统全部的麻烦正是「被认出来是那一类信」（docs/93）。一封信
也意味着**占一个额度、留一条 `send_log`**，日限额、退信抑制、免打扰、每公司上限
全部原样生效，一条都不用重算。

上限两个抄送（`contacts.MAX_CC`）。

## R2：地址只能是官网上印着的

docs/89 的规矩不动：不猜地址。`contacts` 里的地址是 `decision_maker_radar` 从公司
自己的页面上读到的，猜出来的地址从来进不了这张表。

## R3：不确定就不称呼

`personalize.looks_like_a_person` 在名字进入称呼之前挡一道。**宁可漏掉真人，不可
把公司名当人叫出口** —— 漏掉的代价是一封没有称呼的信（今天 393 家的常态），叫错的
代价是这封信从第一行就结束了。

单段的名字照收（`Carlos` 是常态，不是残缺数据）；黑名单挡单段里的垃圾
（`Contact`、`Team`、`Welcome`）。

残留的假阳性还有（`Air Sanitizer` 这种两段普通名词）。写在这里而不是假装没有：
它比「Hi Nationwide,」罕见得多，等真的出现在信里再收。

## R4：老的四参发信器还能用

没有抄送时按 `sender(to, subject, body, image)` 调用，有抄送时才多传 `cc=`。
测试里的假发信器和 `send_via` 的替身都不认识第六个参数，而它们测的是别的东西。

## 验收

1. 一家公司有第二个信箱：`sender` 收到 `cc=['michael@…']`，`send_log` 只有一条。
2. `leads.email` 不因此改变。
3. 只有一个信箱的公司：`sender` 仍按四个参数调用。
4. 信封里 `To` 是原地址，`Cc` 是第二个地址，两个都在实际收件人列表里。
5. `Nationwide Delivery` / `Outside Sales` / `Markdown Content` / `The Team`
   进不了称呼；`Michael Wiener` / `TOM WILSON` / `Carlos` / `윤주영` 进得去。

## 没做的

* **不替换 `leads.email`。** 这是 R1 的全部内容，单列一次因为第一版方案就是替换，
  被 Allen 推翻了，理由比方案好：不知道哪个信箱后面坐着人。
* **不扩大扫描。** 把 393 家冷客户放进 `decision_maker_radar` 的队列、并抬高
  `MAX_SWEEP_ACCOUNTS`，是下一份规格的事 —— 它要先解决名字判断（这份规格只是挡住
  脏名字，没有让脏名字变干净）。
* **不给找到的人单独发信。** 见 R1。
