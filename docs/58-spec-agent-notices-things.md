＃ 58 — 让 Agent 自己看见东西

## 问题不是它不干活

Agent 每天在干活：8/25 建了 245 个任务、完成 124 个，8/26 建了 88、完成 45。它会重读官网、
找决策人、核实公司、修无效渠道。**它不是闲着。**

问题是它**看不见**。它每天重读几百个官网，读完只留下两个数字：

```python
classified = {"icp_type": ..., "fit_score": ..., "hits": []}
```

页面上说的其他一切——他们新上了租赁页、宣布了一个新项目、下个月要去 InfoComm——全部丢弃。

一个销售如果每周把客户官网重读一遍，笔记上只写「工程商 / 70 分」，那不叫在跟进，叫在走流程。
**像人的那一部分，是注意到变化。**

## 根因：一个给历史回填用的开关，在日常路径上一直开着

`recheck.run()` 有个 `first_read` 参数，它的文档写得很清楚：

> `first_read` 是给那批在这套机制存在之前就收进来的老线索做回填用的。对它们来说什么都是新的，
> 全部报「官网变了，值得再碰一次」会把真正的采购窗口淹掉。

而 `autonomous_work._refresh_common`——Agent 每天重读官网走的就是这条路——**无条件地传
`first_read=True`**：

```python
return recheck.run(conn, lead["no"], first_read=True, enrich_fn=...)
```

`recheck.run` 里对应这一行：

```python
new_signals = [] if first_read else _store_new_signals(...)
```

所以 Agent 按代码结构**永远不可能发现任何采购信号**。`buying_signals` 全库只有 5 条，958 个
有官网的客户里只有 70 个 `recheck_count > 0`——这不是巧合，是这个开关。

### R1 常规重读不声称自己是第一次

`first_read` 由这条线索**有没有被读过**决定（`recheck_count == 0`），不由调用方一口咬定。
一次性回填是一次性的，日常路径不该继承它的豁免。

## 但只改这一行会更糟

现存那 5 条信号长这样：

```
公开采购 / RFQ：n+Products) * [+ View All Categories](https:/
渠道 / 经销商拓展：## Let's discuss your project Connect with o
展会参展：you can create immersive 3D environments?
```

这不是信号，是抓下来的 markdown 碎片，而且其中一条重复了两遍。

只放开 R1，958 个客户会立刻灌进来几百条这种东西——**正是 `first_read` 那段注释担心的"淹掉真
信号"，只是换了个方式发生。**两件事必须一起改。

### R2 读不通的摘录不是证据

`_headline()` 从摘录里挑**最短**的句子片段当细节：

```python
detail = min(pieces, key=len) if pieces else excerpt
```

挑最短是有道理的（要一句干净的细节），但在导航密集的页面上，最短的片段**必然**是链接碎片。

细节必须读起来像话：含 markdown 链接、URL、成串括号方括号的片段不算，字母太少、词数太少的
不算。一条都挑不出干净的，**这条候选就不要**——宁可漏掉一个信号，也不要往 Allen 面前放一行
他读不懂的东西。读不懂的信号比没有信号更糟：他得点进去看原文才知道是不是假警报，代价比这条
信号本身还高。

### R3 导航栏和页脚里的匹配，不是关于这家公司的事实

同一句 `View All Categories` 出现在不同公司的信号里，说明匹配点落在了每个页面都有的导航区。
导航文字描述的是网站结构，不是这家公司在做什么。

判据用重复：同一段摘录在**不同域名**上出现过，它就是模板文字，不是事实。

## R4 重读学到的东西要进记忆，不只是两个数字

`lead_memory` 现在 0 行。那套记忆系统本身设计得很好——LLM 提示词要求每条记忆必须引用证据
ID、不许改 Allen 手写的条目、不许推断动机宗教政治健康、不许把沉默当成没兴趣。

它空着的原因是 `memory.update()` **只在客户回信、Agent 起草回复时才被调用**，而全库历史上
只收到过 1 封真回复。

一次官网重读同样是"从外部读到了新东西"，它该和收到回复走同一个入口。这不需要新设计，只需要
把已经建好的入口接到第二个触发点上。

## R5 记下做决定的时候它知道什么

`agent_runs` 只记结果：`{"classify_note": "没有待分类的回复"}`。不记输入。

今天 Agent 说「未触达池最高分只有 58，所以不发任何新邮件」。这个判断对不对，事后没法复查，
因为当时的池子长什么样已经没有了。

借 OpenWorker `session_facts.py` 的那句话：

> 现在记下来，以后问「这条信息会改变当时的判断吗」就能靠重放回答，而不是重新争论一遍

每次 run 记下当时的可发送池大小、最高分、待回复数、退信率。这几个数就是它当天所有判断的依据。

## 不做的事

- 不给信号检测器加新的关键词类别（先把现有的几类做干净）
- 不因为发现信号就自动发信——信号进 `buying_signals`，发不发仍走现有的自主门槛
- 不回填历史：老信号就那 5 条，删掉即可，不值得重建

## 验收

1. 一条已经读过的线索再次重读，信号检测是开着的
2. 一条从没读过的线索首次读取，信号检测是关的（回填豁免仍然成立）
3. 摘录是 markdown 链接汤的候选，一条都不入库
4. 同一段模板文字在第二个域名上出现时，不再作为信号
5. 重读到新东西的线索，`lead_memory` 里能看到，且每条都能说出证据出处
