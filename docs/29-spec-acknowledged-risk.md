# Spec 29 — 人的决定压得住自动闸，但压不住恶化

**Status:** implemented and verified
**Date:** 2026-08-20
**Depends on:** Spec 24（安全闸）、Spec 28（暂停的表达）

## 问题

送达率安全闸每轮 Agent 运行都重新判定一次。Allen 在界面上点「我已了解风险，恢复
自动发信」之后，`set_enabled(True)` 清掉暂停标记，但下一轮 `oversight.evaluate`
看到同样的证据，又把它暂停回去。实测：

```
点恢复后：       enabled=True，暂停已清除
下一轮 Agent 跑完：paused=True，code=deliverability_blind，enabled=False
```

Allen 会陷入「恢复了又暂停」的循环，界面上没有任何东西解释为什么他的决定不算数。

2026-08-20 的现场数据让这个缺陷变成了硬阻塞：退信率 11.4%（阈值 2.0%），且有
30 封从一个未开 IMAP 的邮箱发出、退信无人可读。Allen 看过完整证据后决定继续发。
在当前实现下，这个决定无法执行。

## 规则

### R1 确认是对具体证据的确认，不是对开关的确认

`autosend.acknowledge(conn, pause)` 记录 Allen 确认时的**证据快照**：暂停代码、
当时的退信率、确认时间。存在 `autosend_risk_ack`。

确认的语义是「我看过这些数字，接受在这个水平上继续发」，而不是「以后别再拦我」。

### R2 已确认的风险不再重复暂停

`oversight.evaluate` 在判定暂停前先读确认记录。若当前触发原因与已确认的一致，
且证据没有恶化，则不暂停，并在返回值里带上 `acknowledged`，让运行记录留下
「本轮因 Allen 已确认而放行」的痕迹——跳过的是暂停，不是审计。

### R3 恶化会收回放行

出现下列任一情况，确认失效、重新暂停、清除确认记录：

- 退信率比确认时**高出 1 个百分点以上**（`ACK_TOLERANCE_PCT = 1.0`）。发信继续、
  退信继续，退信率在同一批名单上小幅波动是正常的；持续走高不是。
- 触发原因换了（`code` 不同）。Allen 确认的是「监测不到退信」，不等于确认
  「退信率翻倍」。

理由：Allen 要的是「按我的判断继续发」，不是「关掉安全带」。他确认的是一个具体
的风险水平；风险水平变了，这份确认就不再覆盖它，系统应该重新问他一次。

### R4 关掉自动发送就是撤回确认

`set_enabled(conn, False)` 清除确认记录。人主动停下来，之后再开就该重新看一遍
当时的数字。

## 界面

暂停横幅上的恢复按钮沿用既有的 `acknowledge_safety_risk` 参数，不新增交互。
恢复成功后，横幅换成一行常驻说明：确认时的退信率是多少、以及退信率涨过哪个数
会重新暂停——让 Allen 知道这份放行的边界在哪，而不是以为闸门被永久关掉了。

## 不做什么

- 不改 `BOUNCE_DANGER_PCT`（2.0%）。阈值代表的是行业送达率现实，不因某一次决定
  而改写；要改的是「人能否在知情后越过它」。
- 不自动确认。没有任何代码路径可以替 Allen 调用 `acknowledge`，它只能由带
  `acknowledge_safety_risk=true` 的请求触发。
