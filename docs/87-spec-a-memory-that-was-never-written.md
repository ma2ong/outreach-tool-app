＃ 87 — 一套写好了、但一行都没存过的记忆

## 从「看看那个项目有什么可借鉴」查出来的

Allen 让我看 [munder-difflin](https://github.com/chaitanyagiri/munder-difflin) ——
一个把多个编程 CLI 编排成协作 agent 群的桌面应用。它的多数机制这套系统已经有了：
分级自主权、人工审批队列、可审计的行动台账、worktree 隔离。

它有一条是真的不一样：**记忆从所有活动里持续沉淀**。照着这条去查自己的，发现：

```
lead_memory        0 行
lead_memory_items  0 行
```

## 病因：记忆只在一个几乎不发生的时刻写入

`memory.update` 全项目只被调用一次，在 `run._draft_proposal()` —— 也就是
「客户回信了，**而且** agent 决定起草回复」。这条路走过的次数足以产出 1105 条提议，
却**一条记忆都没写过**。

而书里早就存着 2373 条「客户身上发生了什么」：

| | |
|---|---|
| `send_log` | 944 |
| `activities` | 1089 |
| `relationship_events` | 301 |
| `inbox_messages` | 39 |

其中 22 条 `relationship_events` 的 `kind='fact'` 写着
「银行到账 USD 22,860（2026-08-26）」、「这笔是货代代付，真正的买家另有其人」。

**关于一个客户最该知道的事，明天发给它的信一无所知。**

`memory.py` 的设计本身没问题 —— 每条事实一行、带来源、synthesis 只返回变化，
所以没人动的那条不会被覆盖。文件开头写得清清楚楚为什么要这样。
坏的是它的入口，不是它的形状。

## R1：事实在发生的那一刻就写下来，不等 synthesis

三个入口，都不调模型：

* `relationship_events.record(kind='fact')` —— 到账、角色纠正、硬性限制，写完即入记忆
* 回复入库时（`replies._store`）—— 回复本身就是一件发生过的事
* `memory_events.catch_up()` —— 把已经躺在库里的历史补上

**不调模型是有意的。** 这些是书里已经用人话记下来的事实；让 LLM 复述一遍只会增加成本、
延迟，和一次说错的机会。「这条回复**意味着**什么」仍然归 synthesis，
「发生了什么」归这里。

## R2：不记流水账

发信不进记忆。「我们发了第 2 封」在 `outreach` 行上已经有了，
一份复述活动日志的记忆是没人会读的记忆。

进记忆的是**一个人会记住的东西**：他们付过钱、他们退过信、他们回过什么话、
他们说了「我已经在跟 Tony 买」。

## R3：每一条都要能说出出处

[docs/45](45-spec-no-claim-without-a-source.md)。事件项带 `event:12` / `inbox:7`，
和 synthesis 写的那些用同一套校验 —— `_EVIDENCE_TABLE` 加了
`relationship_events` 这一项，一条指不到真实行的证据会被整条丢掉。

出处同时是**幂等键**：一个已经被在世条目引用过的事件不会再写第二遍，
所以每个周期跑一次、全量补一次，都不会重复。

## 没做的

* **成本记账。** `llm._record()` 只记「哪个后端今天调了几次」，不记 token、不记钱、
  当天清零、不留历史。而 `cli_limit=200/天` 这道闸是按**次数**拦的 ——
  一次调用可能 500 token 也可能 20000，用次数当预算等于没有预算。
  12 天 78 次 LLM 调用，量还小，等 agent 用得多了再做。
* **失控熔断器。** 那个项目有，这套系统不需要：1105 条提议 1104 条执行成功、
  789 次运行 0 失败、没有重复空转。
