# 114 — 一个人两个信箱，不是两个人

## 一次录入

DJC West 这条客户下面挂着两个联系人：

| 联系人 | 邮箱 | 角色 |
|---|---|---|
| Javier Carlos（主要） | javier@djcwest.com | 决策人 / 采购 |
| info@djcwest.com | info@djcwest.com | 其他 / 未确认 |

第二行不是一个人。它是 Javier 的另一个信箱——官网联系页上写的那个总箱，
[decision_maker_radar](../backend/app/decision_maker_radar.py) 从站上读到，
库里没地方放，就只好新开一行。

这带来两个后果，都不是小事：

- **统计说这家公司有两个联系人**。`contacts.stats` 数的是行，不是人；
  「决策人覆盖率」「已具名联系人」全部按行算，一个人被数成两个。
- **每个 UI 都要显示两遍**。客户抽屉、报价单收件人、话术个性化对象、
  Agent 的 customer360，都在问「这家公司的联系人是谁」，答案永远多一个。

反过来，把 `info@` 删掉也不行：那是同一个人真实可达的第二个地址，
[docs/95](95-spec-two-mailboxes-one-letter.md) 抄送用的正是它——删了就是主动
丢掉一条送达路径，而 Allen 不知道哪个信箱后面真的坐着人。

**缺的是「一个人可以有多个联系方式」，不是「多建几个人」。**

## R1 主联系方式不变，附加的挂在旁边

`contacts.email` / `contacts.phone` 仍然是这个人的默认地址：同步进 `leads`
（`_sync_lead`）、群发的收件人、报价单抬头，全部走它，一行代码都不用改。

附加地址进新表 `contact_channels(contact_id, kind, value, status)`，
`kind` 只有 `email` 和 `phone` 两种。

这么分是因为「默认对象」这件事已经在系统里生效了——主要联系人决定发给谁，
主邮箱决定发到哪。附加地址要解决的是**认得出**和**抄送得到**，不是再开一条发信路径。

## R2 他从哪个信箱回信，都算他回的

四条识别路径要认这些附加地址，否则加进来等于没加：

| 函数 | 认不出的后果 |
|---|---|
| `find_email` | 从 `info@` 回的信挂不到 Javier 名下，只挂到公司 |
| `email_leads` | 连公司都对不上，回信进不了收件箱的已知客户 |
| `find_phone` / `phone_leads` | 第二个号码发来的 WhatsApp 认不出是谁 |
| `also_reach`（[docs/95](95-spec-two-mailboxes-one-letter.md)） | 抄送名单里少一个地址——恰好是今天已经在抄的那个 |

`also_reach` 这条要特别说清楚：今天 `info@` 被抄送，是因为它是同公司的另一个**联系人**。
把它并成 Javier 的第二个信箱之后，抄送必须照旧，否则这次整理的净效果是少发了一个地址。
上限仍是 `MAX_CC = 2`，仍跳过 `invalid`，仍是一封信、一个额度、一条发信记录。

## R3 同一家公司里，一个地址只能属于一个人

`idx_contacts_lead_email` 保证了同公司主邮箱不重复。附加地址进同一个命名空间：
往 Javier 下面加一个地址前，先查这家公司有没有别人（主邮箱或附加地址）已经占着它。

占着的时候，答案不是报错。Allen 的原始动作就是「这两行是同一个人」——
系统看得见那一行是谁，就该问出口：

> `info@djcwest.com` 已经是这家公司的另一个联系人。把它并到 Javier Carlos 下面？

确认之后走 R4，取消就什么都不做。直接报「已存在」等于把已知的答案藏起来，
让 Allen 自己去删一行——而删除会把那行的往来信件变成无主消息。

## R4 折叠一个联系人，不丢它带来的东西

把联系人 B 折进联系人 A：

- B 的主邮箱、主电话变成 A 的附加地址（B 自己的附加地址一起搬过来）
- B 名下的收件消息、报价单、订单、Agent 提案改挂到 A
- B 的姓名、职位、LinkedIn、备注只填 A 的空缺，不覆盖 A 已有的值
- 删掉 B

前三项里，**Agent 提案（`agent_proposals.contact_id`）是今天 `_fold_into` 漏掉的**——
公司查重合并时它就已经会留下指向已删联系人的悬空 id，只是没人注意。
折叠从这条 spec 起会常用，一并补上。

B 是主要联系人时不允许折叠：主要联系人是发信的默认对象，
换主要联系人是一个独立的、看得见的动作（「设为主要」），不该藏在「加个邮箱」里发生。

## R5 第二个地址长得就是第二个输入框

联系人卡片里，邮箱和电话各自的标签后面跟一个 `＋`。点开是一个输入框和一个「添加」，
添完之后它就排在默认地址**正下方，同宽的第二个框**——邮箱 1、邮箱 2，一列到底。

不是一行灰字加两个按钮。字段列只有 180 像素宽，按钮并排放会把地址挤掉一截，
而看不全的地址等于没显示；更要紧的是，一个躺在输入框列里的值，人会去点它、改它。
所以它就是输入框：**改完失焦即存**，两个动作缩成图标浮在框内右端：

- **★ 设为默认**——和主地址对调（主地址降为附加地址）。这会改 `leads.email`，
  也就是改群发的收件地址，所以它是显式动作，不是加地址的副作用。
- **× 删除**——删掉这个附加地址。删的是一条记录，不是一个人，不需要二次确认。

改成同公司别人占着的地址会被拒绝（R3），但**编辑不触发合并**：
合并只在「添加」那一步问，一条路径一个入口。

附加地址不参与「主要 / 次要联系人」的判断，也不出现在联系人计数里：
`contacts.stats` 数的仍是人。

`contact_channels.status` 今天只有两个来源：合并时从被并掉那个人的 `email_status`
继承，以及和默认地址对调时跟着地址走。**退信不会自己写进来**——`bounced_at`
和 `email_status` 都挂在客户行和联系人行上，抄送地址退信本来就没人记，
这是 [docs/95](95-spec-two-mailboxes-one-letter.md) 起就有的缺口，
不是这条 spec 造成的。手动把某个地址标成 `invalid` 会立刻让它退出抄送名单，
自动标注要等抄送退信有地方可记时再说。

## R6 老库不用迁移

`contact_channels` 建出来就是空的。今天分成两行的联系人保持两行——
系统不替 Allen 判断哪两行是同一个人（[docs/109](109-spec-the-same-company-two-rows-only-a-human-can-see.md)
是同一个道理：合并不可撤销，宁可漏不可错）。他哪天看到那两行，
在 Javier 下面敲一次 `info@`，R3 就会问他。
