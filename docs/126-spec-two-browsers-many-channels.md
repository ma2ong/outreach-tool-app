＃ 126 — 两个浏览器，很多渠道

[docs/124](124-spec-the-directory-page-a-crawler-cannot-read.md) 把 browser-use 接进来时，只接了一个用途：
读一个抓不动的名录页。[docs/70](70-spec-discovery-channels.md) 把渠道做成了声明，
但四条声明里三条是 Naver，全球市场实际只有 DuckDuckGo 一条腿。

这两件事的共同前提是错的：**浏览器不是某一个渠道的补丁，它是一种读法。**
搜索引擎、社媒、博客、名录，都可以用三种读法里的任意一种去读。

## 2026-09-10 实测：便宜的读法在哪些渠道上还够用

同一天，同一个关键词（英文 `LED display distributor` / 韩文 `LED 전광판 유통업체`），
只用现在的 `jina.fetch`：

| 渠道 | 结果 | 够不够 |
|---|---|---|
| DuckDuckGo | 9 个域名 | 能跑，但见下 |
| Naver 网页 | **11 家真实韩国公司**：pst24.co.kr、ganpanlab.kr、kioskkorea.kr、bhinfo.co.kr…… | 够，别动 |
| Naver 博客 | 链接里 **0 家新公司**（3 家与网页搜索重复，1 个 openstreetmap.org） | 不够 |
| Google | 704 字节，`This page maybe requiring CAPTCHA` | 完全不够 |
| Bing | 4672 字节外壳，两次都一样，结果链接取不到 | 不够 |
| Instagram | HTTP 403 | 不够 |
| Facebook | 反爬页 | 不够 |

DuckDuckGo 那 9 个要单独说：unit-led.com、doitvision.com、eagerled.com、linsnled.com、
minrayled.com、pixelflexled.com——**这些是同行**，是跟迈彩抢客户的中国 LED 厂。
9 个里只有 arrow.com 一家算渠道商。

同一天 Naver 那 11 个是 pst24、간판랩、키오스크코리아这类**韩国本地招牌和显示工程公司，
是真正会买屏的人**。

结论不是「便宜的读法不好」，是：**唯一一条免费又无人值守的全球渠道，产出以同行为主；
产出买家的那些渠道，恰好都要浏览器。** 这就是这份 spec 要花的钱。

## R1 三种读法，按成本排队，由渠道自己声明支持哪几种

| 读法 | 成本 | 能不能无人值守 | 什么时候用 |
|---|---|---|---|
| `http`（jina） | 免费 | 能 | 名单在 HTML 里 |
| `playwright` | 免费，但每站要写选择器 | headless 能，登录态不能 | 结构稳定、每天都要跑 |
| `browser`（browser-use + DeepSeek） | 每步一次模型调用，85–121 秒 | **不能** | 结构不稳定、有反爬、或者要读正文 |

两个引擎不是二选一，是**便宜的先跑，贵的按需**。这正是 docs/124 R4 在名录页上已经做的：
抓到 0 家才出现「用浏览器读这一页」的按钮。这条推广到所有渠道。

Playwright 和 browser-use 的分工不按渠道分，按**页面结构稳不稳**分：
Naver 的搜索结果页十年没大改，写选择器划算；Instagram 的 DOM 每季度换一次类名，
写选择器就是每季度返工，交给模型看反而便宜。

## R2 模型说出来的名字是一条查询，不是一条记录

docs/124 R1 立了一条红线：**只有域名能过界**，因为模型把
`syscom-cloned-21865-Avientek-Logo--768x134.png` 读成过公司名。

Naver 博客把这条红线顶到了墙上：那 73KB 正文里有「진영LED전광판」这样的公司，
**它根本没有链接**——韩国中小公司在博客上做生意，名字写在正文里。
只收域名，这条渠道就等于不存在。

解法不是放宽 R1，是给名字换一个身份：

> 模型读出来的公司名，不写进任何表，而是**当作一条查询**丢回 `naver-web` 去搜；
> 搜到的站**必须自己说出这个名字**，才算数。
> 确认不了 → 这个名字就地消失，什么都不留下。

后半句是实测逼出来的。这份 spec 初稿写的是「搜不到就消失」，**这句话是错的**——
2026-09-10 实测，搜索引擎永远会热心地回答点什么：

| 查询 | Naver 返回 | 真相 |
|---|---|---|
| `진영LED전광판` | bandyled.com | 另一家公司。反딧불 LED 是**写博客的那个安装商**，진영 是它文章里的客户 |
| `키오스크코리아` | kioskkorea.kr | 域名字面撞上了，那家公司其实叫**키코**，标题写着 `키코 \| LED 전광판 업체` |
| `이런회사는없습니다주식회사12345`（现编的） | etoland.co.kr | 纯属瞎编的名字，配到了一个真实网站 |

**「搜不到」这个筛子根本不存在。** 加上「站自己得提到这个名字」之后，上面三条全部被挡掉，
Absen → absen.com 仍然通过。

代价是这条渠道产出很低：韩国中小企业的站大多是 JS 渲染的，jina 读回来是空的
（实测 kioskkorea.kr 只有 64 字节），读不到就等于确认不了，一律丢弃。
这符合 docs/124 R6 已经立过的规矩：**收得不全是可接受的，收错是不可接受的。**

（现有 `naver_local` 会写 `domain: "naver-local:<名字>"` 存一个没验证过的名字，
那是这条规则之前的做法，本 spec 不动它，但新渠道一律不许这样。）

## R3 浏览器不离开渠道自己的域

docs/124 R3 的白名单是「目标名录页那一个 host」。搜索渠道看起来要打破它——
搜完总要点进结果吧？

不用。**结果域名就印在结果页上**，浏览器读完就够了；真正去访问那些公司官网的是
`enrich_domain`，走的是普通 HTTP，不是这个浏览器。

所以白名单规则不变，只是换个算法：**渠道自己的 host**，不是目标公司的 host。
Google 渠道放行 `*.google.com`，Naver 渠道放行 `*.naver.com`，名录页渠道放行那一页的 host。

白名单仍旧由调用方从渠道声明里生成，**永远不接受任务提示词里出现的域名**。
docs/124 实测过模型在页面卡住时自己想跑去 DuckDuckGo 和 Bing，两次都被
`blocked by security policy` 拦下——那道拦截是这条规则唯一的实现方式。

## R4 采集用的浏览器身份，和发送用的身份物理隔离

`playwright_engine.py` 现在用 `~/.outreach-tool/browser/<channel>`，
里面是 WhatsApp / Instagram / Facebook 的**发送登录态**。

采集**不许碰这个目录**。它有自己的 `~/.outreach-tool/scrape/<channel>`。

理由不是洁癖。平台对「已登录账号的自动化批量浏览和搜索」的风控，比对发消息本身更敏感——
浏览量能瞬间做到人类做不到的量级，特征太明显。而这套系统里：
服务器挂了能重装，数据库坏了有备份，**Instagram 账号封了买不回来**。

采集拿一个可以赔的身份去跑，发送那个不能赔的身份完全不进采集代码路径。

## R5 只有能无人值守的读法才进调度器

每条渠道声明 `unattended`：

- `http` 读法、headless 的 `playwright` 读法 → 可以进 autosend / Agent 的定时发现
- 任何会弹出可见窗口的读法（`browser` 全部、要登录态的 `playwright`）→ **只在 Allen 按按钮时跑**

docs/124 R4 的理由原样成立：一个会在凌晨三点弹窗抢焦点的东西，
不该由定时器决定什么时候弹。

## R6 没登录 = 未启用，不是失败

沿用 docs/70 R4 和 docs/124 R5。Instagram / Facebook 采集渠道**现在就注册进去**，
在 `~/.outreach-tool/scrape/` 里还没有登录态时，它报的是
「未启用：需要先登录采集专用账号」并说明怎么登，不是异常、不是重试、不是空结果。

一条没配好的渠道和一条坏掉的渠道，在界面上必须是两回事。

## 不做的事

- **不替换 DuckDuckGo 和 naver-web**。它们免费、无人值守、每天在跑，没坏
- 不给结构不稳的站写 Playwright 选择器。那是每季度返工，不是一次投入
- 不用发送账号做采集（R4），一次都不行
- 不让任何 `browser` 读法进调度器（R5）
- 不做需要付费 API 的搜索渠道。这条 spec 解决的是「不花钱能不能拿到买家」

## 验收

1. 一条渠道声明支持哪几种读法；`/api/discover` 指定读法时按声明校验，未声明的读法报 400
2. `browser` 读法的白名单只含**渠道自己的** host，且不来自任务提示词
3. 采集从不打开 `~/.outreach-tool/browser/` 下的任何 profile（R4）
4. 任何调度器代码路径都到不了 `unattended=False` 的渠道（R5）
5. Naver 博客渠道返回的公司名，先经 `naver-web` 解析成域名、且**那个站自己提到这个名字**
   才落库；确认不了就丢弃（R2）。模型读出来的名字本身不进任何表
6. Instagram / Facebook 在没有采集登录态时报「未启用」并说明怎么登，不返回空结果（R6）
