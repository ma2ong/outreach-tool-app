# 48 — 出门前的闸门，和一个不制造噪音的 Agent

两条规则，一条守住发出去的内容，一条守住 Allen 的注意力。都来自同一个观察：写在提示词里
的准则，模型和写模板的人都可能忘，而运行时的计数器不会。

## 触发这份 spec 的两个事实

- 544 封开发信，**0 封真人邮件回复**（17 封退信、2 封自动回复）。第一封信的主题是
  `Recent LED Display Projects — Shenzhen Maxcolor Visual`，正文第一句是"我们在韩国
  交付的项目"——发给美国、巴西、智利的集成商。而这些客户里 69% 带着一条从他们自己
  官网上读来的 `hook`，没有任何一个模板用过它。
- 销售任务积压 89 条，其中同一句话出现三遍，日期是 08-21、08-24、08-25。计划器
  只在当天内去重，所以同一件没做完的事，每天早上都被当成新任务建一遍。

## 规则

### R1 检查真正发出去的那段文字，不是有人审过的模板

`message_guard.check()` 在 `render()` 之后、`sender()` 之前跑。理由很简单：模板里写着
`{hook}`，客户读到的是渲染后的句子，而**没有人审过渲染后的那一版**。

两条不变量：

**价格。** `AGENTS.md` 第一条铁律是 Allen 独占定价。在此之前这条只活在提示词里，而
手写模板和模型草稿都可能带价格。匹配范围刻意收窄——`P2.5`、`200 sqm`、`+86 135...`
是正常开发信里到处都是的数字，把它们拦下来会让人把闸门关掉。

**个性化，只管第一封。** 一封谁都能收的信不是开发信，是邮资，而且它花的是发件信誉。
第二、三封挂在第一封的主题下，再重复一次钩子读起来像机器人，所以这条只在 `step_order == 0`
时生效。

匹配用整词，不用子串：两个字母的公司名否则会匹配到正文里任何一个孤立字母——和 45 号
spec 里 `Indiana` 读成 India 是同一个坑。

被拦下的不改写、不放行，只报告：**一封被悄悄改过的信，是没有人真正审过的信。**

### R2 拦下来要说清为什么

`send_campaign` 和 `send_due` 的返回里带 `held` 和 `holds`，界面上跟"成功/失败/延后"
一起显示，逐条写明是哪家、什么原因。一个只报"发送 0 封"的闸门，会让人翻半天日志去
找一条正在正常工作的规则。

### R3 自己醒来的 Agent，在上一件事做完之前没有新话要说

一个客户同时只有一条未完成的 Agent 任务。Allen 自己建的任务不算——那是他的备忘，
不是 Agent 的待办请求；把开着的那条做完，这个客户就重新可以接收下一条。

这条规则的实质不是"少说话"，而是**没有新东西就不要重复说**。第 89 条待办不会有人读，
它的存在只是让前 88 条也一起失去可信度。

### R4 来源在产生的时候记，不靠事后反推

Agent 建任务时直接写上 `source='agent'` 和 `source_ref='proposal:<id>'`。在此之前
Agent 建的任务和 Allen 手敲的长得一模一样，以至于 PR #9 要靠**把执行器自己写的那句
中文结果从提议里解析回来**才能认出归属。

## 配套改掉的模板

英语序列第一封改了：主题从自报家门（`— Shenzhen Maxcolor Visual`）换成
`{company} — LED display supply`，正文用 `{hook}` 开场，删掉发给美国人的韩国案例。

对真实队列试跑：178 家通过，3 家被拦，而这 3 家的"公司名"分别是
`LED Display Manufacturer`、`Professional LED Display Solutions` 和 `Tradekorea`
——两条是描述不是公司名，一条是 B2B 平台。闸门没有误伤，顺手指出了该清理的记录。

## 验证

- `tests/test_message_guard.py`：五种写法的价格都被拦；`P2.5`/`200 sqm`/`+86` 不算价格；
  完全通用的那封信被拦；用了公司名或 hook 的通过；第二封不再被要求重新自我介绍。
- `tests/test_agent.py`：同一客户第二条 Agent 任务不建；做完之后可以再建；Allen 自己
  建的任务不会让 Agent 闭嘴。
- 存量清理：24 条重复待办已取消，未完成任务从 89 条降到 65 条。
