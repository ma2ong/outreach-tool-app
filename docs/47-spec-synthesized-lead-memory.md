# 47 — 客户记忆是合成出来的，不是每次重写的

## 现在的做法为什么会忘事

`lead_memory` 一个客户一行，`summary` 一段不超过 200 字的散文。每次客户回信，
`agent/memory.py` 把旧摘要连同新邮件一起丢给模型，让它**重写整段**。

这套做法有四个后果，都是静默的：

1. **每次重写都可能丢东西。** 200 字装不下三个月的往来，新信息进来就得挤掉旧的，
   挤掉哪一条由模型每次临时决定。客户三月说过"预算要等 Q3"，到第五次重写时
   可能已经不在了，而且没有任何地方记录它曾经在过。
2. **没有出处。** 摘要是一段话，没法回答"这句是从哪封邮件来的"。写错了看不出来，
   也无从更正——这正是 [45](45-spec-truthful-lead-facts.md) 里那类"系统写了它并不
   知道的事"。
3. **持久的事实和有时限的事实混在一起。** "他们只用 WhatsApp 沟通"和"这周在
   拉斯维加斯参展"写在同一段话里，同等对待。一周后后者是错的，前者仍然是对的，
   但没有任何东西能区分它们。
4. **Allen 说的话没有特权。** 今天没有让人手写一条记忆的路径；就算有，下一次模型
   重写也会毫不犹豫地把它抹掉。

## 规则

### R1 记忆是一组带出处的条目，不是一段散文

一个客户的记忆由若干条独立条目组成，每条：

- `kind`：`profile` 是持久的（身份、偏好、约束、关系、沟通方式），`log` 是有时限的
  （项目、决策、报价、行程、当前卡在哪）。
- `content`：一句能独立成立的事实，500 字符以内。
- `origin`：`explicit` 是 Allen 手写的，`synthesized` 是 Agent 合成的。
- `evidence`：这条事实依据哪些互动，形如 `inbox:1200`、`note:57`。

`lead_memory.summary` 保留，但不再是被重写的正文，而是**从条目渲染出来的视图**。
`draft.py` 和 `/api/agent/leads/{no}/memory` 的调用方因此一行不用改。

### R2 写不出出处的事实不许写进记忆

每条 create / update 必须引用至少一个真实存在的证据 ID，落库前逐个核对
`inbox_messages` / `notes` 里确有其行。引用不上的变更整条丢弃，不是截断后保留。

理由和 45 号 spec 同一条：**猜出来的事实和查出来的事实混在一起之后，就再也分不开了。**
一条没有出处的记忆会原样进入下一封开发信，而没有人能追溯它是怎么来的。

### R3 变更是增量的，不是整体重写

模型返回的是变更列表而不是新正文：

```json
{"changes": [
  {"action": "create", "kind": "profile", "content": "...", "evidence": ["inbox:1200"]},
  {"action": "update", "id": 12, "content": "...", "evidence": ["inbox:1201"]},
  {"action": "remove", "id": 7, "evidence": ["inbox:1201"]}
]}
```

没有提到的条目保持原样。这是"忘事"和"记得住"的分界：整体重写里，一条事实活不活
取决于模型这次有没有想起它；增量变更里，一条事实要消失必须有人明确地删掉它，并且
说明依据。

`remove` 不删行，只标记 `superseded_at`。被推翻的事实本身是有用的历史——客户改过
主意这件事，比他现在的主意更能说明问题。

### R4 Allen 写的记忆，Agent 不许改也不许删

`origin='explicit'` 的条目只有 Allen 能动。合成时它们照常作为上下文参与判断，但
针对它们的 update / remove 一律丢弃。

一个人明确记下来的东西，通常正是模型从对话里看不出来的东西（"这家老板不喜欢被追"）。
让自动流程能覆盖它，等于让系统忘掉唯一真正可靠的那部分。

### R5 时间只用来推移，不用来编造

合成时告知今天日期。一条带日期的 `log`（"下周去看厂"）可以随时钟推移改写为已过去，
但**不许推断这件事到底有没有发生**。"计划中"变成"曾计划"是时间的事实；"去过了"
是只有客户能告诉我们的事实。

### R6 不猜没说出口的东西

只写输入里明确存在的事实。不推断动机、不推断敏感属性（宗教、政治、健康）、不把
"没回邮件"读成"不感兴趣"。不确定就保留不确定，或者不写。

### R7 用规则校验，不用第二次模型调用审计

（这条是与 Grok Bot 做法的自觉分歧，写下来是为了以后不被"它是这么做的"说服。）

Grok Bot 的记忆合成会再调一次模型审计变更提议。这里不这么做：本项目的变更空间小得多，
R2/R4/R5 都是可判定的——证据 ID 存不存在、条目是不是 explicit、条数和长度超没超——
确定性校验既比模型审计可靠，又不花第二次调用的钱和时间。

上限：一次合成最多 12 条变更，一个客户最多 40 条有效条目（超出时最旧的 `log` 先退役，
`profile` 和 `explicit` 永不自动退役）。

## 验证

- `tests/test_agent_memory.py`：引用不存在证据的变更被丢弃；explicit 条目挡住来自
  合成的 update/remove；`remove` 之后条目仍在表里但不进 summary；没提到的条目在
  一次合成后原样保留（这是老做法会丢事实的那个场景）。
- 渲染出的 `summary` 仍然是 `get_memory()` 的一个字段，`draft.py` 不用改。
