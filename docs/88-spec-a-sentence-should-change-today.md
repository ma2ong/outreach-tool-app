＃ 88 — 一句话应该能改变今天做什么

## 从「Grok 的 BOT 有什么可借鉴」来的

Allen 拿来一段讲 SuperGrok Heavy 的话，核心三条主张：agent 是一个有名字有职责的
「人」而不是一次性对话；BOT 之间底层打通、权限给高、自己协调；流程在工作里自然沉淀，
而不是先设计好流程再开工。

照着这三条查自己的。第一条这套系统的等价物已经有了（`control_center` 就是一张统一
作战图），第二条**明确不要**（理由在最后一节），第三条指向一个真的缺口。

## 系统不缺执行力，缺的是改主意的入口

八个动作类型全部在 `auto`：

```
agent_autonomy_reply_draft / send_outreach / create_task / enroll_sequence
/ stop_sequence / discover_run / build_opportunity / mark_do_not_contact  = auto
```

于是提议队列里 **pending 是 0**。它已经不是一张决策桌了，是一条执行流水线。

| | |
|---|---|
| `agent_proposals` | 1105（其中 `create_task` 1081，失败 1）|
| `agent_runs` | 793 |
| `activities` status=open | **711**（agent 自己欠着 584，人欠着 126）|
| 其中建于 2026-08 | 704 |

这些数字说的是同一件事：**跑是跑得动的，1104 条提议执行成功、793 次运行 0 失败。**

而 584 条 agent 自己欠着的任务里，579 条的 due date 是**它自己排的**：

```
跟进 Navraykorea：先重新读取官网并完成 ICP 分级…    | 2026-09-04
跟进 Pantallas LED Mexico：…                       | 2026-10-01
```

排期是它定的，**改期没有入口**。今天想说「先把韩国那批做了」「这套开场白重写，
别提价格」「这家别再碰了」——没有一句话能说到系统里。唯一的路径是打开 14 个 tab
里的某一个、筛选、逐条点。docs/86-R3 已经点过这个形状：「客户开发排在 14 个入口的
第 12 位」。当时的修法是给空库一张卡；这次要修的是**非空库**。

## R1：一句话只落到一份写死的白名单上

不生成代码、不自由调函数、不改配置。一次模型调用只做一件事：把原话映射成
`{action, args, confidence}`，`action` 不在白名单里就走 R3。

**只读**（直接从 `control_center` / `sales_truth` 取数答，不落库、不产生提议）：

* `today` — 今天什么情况
* `stuck` — 谁卡住了、哪条渠道没产出（86-R2 已经有这个判断）
* `lead` — 某家客户现在到哪一步了
* `why` — 这条提议/任务为什么在这

**写入**（全部经 `proposals.create`，**一条新的执行路径都不加**）：

* 复用已有的 7 个 kind：`create_task` `enroll_sequence` `stop_sequence`
  `discover_run` `mark_do_not_contact` `send_outreach` `reply_draft`
* 新增一个 kind：`reschedule_work` —— 改 `activities` 的 `due_at` / `priority`，
  或取消。理由就是上面那 579 条：**排期是 agent 定的，没有改期入口的排期不是排期，
  是一堵墙。** 它不发任何外部消息，风险 `low`。

写入动作全部落在 `executors.HANDLERS` 上，命令入口一条新的执行分支都不加 ——
`test_every_command_action_lands_on_an_existing_executor` 盯着这一条。

白名单本身写在代码里、不可由命令扩充。「能力清单能不能改」和「今天做什么」是两个
问题，后者归这个入口，前者归 docs/86 的那道门（先写编号规格）。

## R2：命令产生的提议一律 pending，不吃 auto

`auto` 是给按代码路径跑的 agent 的：同一段代码、同样的条件、可预测，所以八个开关
敢开。一句自然语言被理解错的概率是另一个量级 —— 而 `send_outreach` 在 `auto` 上
意味着**理解错了的时候，信已经发出去了**。

所以命令入口调 `proposals.create` 时**强制 pending，不读 `agent_autonomy_*`**。
屏幕上回一句：

```
我理解成：给 12 家韩国客户停掉跟进。
动作类型 stop_sequence   影响客户 12 家   市场 South Korea
[执行]  [算了]      待确认 —— 在你点之前什么都没发生
```

点了才走 `proposals.approve` → 已有执行器。

这不是多一次点击，这是这个入口**唯一的安全内核**。绕过它，命令行就成了一条不受
docs/15、docs/48、docs/49 约束的第二条执行路径 —— 而 `control_center` 的开篇写着
为什么这套系统聚合已有真相、不发明第二个执行器。

## R3：听不懂就说听不懂，不猜

置信度低于阈值、指代不明、白名单之外 —— 回一句「不确定你说的是 A 还是 B」或
「这件事我做不了，你要的可能是 X」。**不选一个最像的执行。**

命中白名单但参数缺（哪个市场？哪条序列？）同样回问，**不填默认值**。
AGENTS.md 的原话：低置信度是停下来问的理由，不是猜的理由。

## R4：数量要在点击之前说出来

「韩国那批」可能是 4 家，也可能是 460 家。提议卡片必须先写清楚**这一句话会碰到
多少个客户、走哪个渠道、扣哪个日限额**，再让人点。

这条是给 `send_outreach` / `enroll_sequence` / `stop_sequence` / `reschedule_work`
用的。一句模糊的话乘以 460，是这个入口最现实的事故形状 —— 比理解错动作类型现实得多。

## R5：命令台账

一张 `agent_commands`：原话、解析出的 action 与参数、置信度、生成的 proposal id、
最后结果。

两个用途，第二个才是重点：

* 出事能回溯「他到底说了什么、我理解成了什么」；
* 这份台账是「重复三遍就该固化」的原料。**同一句话说到第三遍，就该有人提议把它
  变成一条规则或一个按钮**，而不是继续每天打一遍。那段话里「流程在工作中沉淀」
  说的就是这件事，而沉淀需要先有记录 —— 这跟 docs/87 是同一个病：机制建好了，
  入口不写，表就永远是 0 行。

## R6：入口在 Agent 页顶部，不新增页面

14 个 tab 一个都不动、一个都不删。命令行不是第 15 个入口，它是**前 14 个的快捷方式**。

真用起来之后哪些 tab 变成了死页面，R5 的台账会自己说。**先有用法，再谈重构导航**
—— 反过来就又是「先设计流程再开工」。

## 验收

1. 八个开关全在 `auto` 时，一句「给韩国那批发一轮」产生的提议状态是 `pending`，
   且没有任何消息发出。
2. 「把这批推到下周」改的是 `activities.due_at`，且留下一条 `reschedule_work`
   提议记录 —— 直接 UPDATE 不留痕的实现不算通过。
3. 一句听不懂的话产生 0 条提议、0 次外部调用，回复里带着「我不确定」和两个候选。
4. 一句没写市场的「停掉序列」回问，不落库。
5. 提议卡片在执行前显示受影响客户数；把范围从 4 家改成 460 家，卡片上的数字跟着变。
6. 命令入口不引入新的 `HANDLERS` 分支：写入动作全部落到已有执行器 +
   `reschedule_work` 一个。

## 没做的

* **手机上指挥。** 提过一轮，查完撤回：`agent_report_push` 默认关着，
  `agent_report_last_date` 停在 **2026-08-25** —— 日报已经八天没往手机上推过，
  而且它现在领着仪表盘（86-R3）。给一条没人在看的消息加回复通道，是给没人走的路
  修桥。先让桌面入口跑出真实用法、`agent_commands` 攒够数，再决定要不要让日报可回复。
* **拟人化的多角色。** 那段话最抢眼的主张，先推荐过、看完代码后撤回。
  `control_center` 已经聚合了提议台账、对话归属、Account Brain 和 Opportunity
  Coach —— 角色只是给这张图加一个分组维度，代价是 mission 拆四段、proposal 加
  `role` 并回填 1105 条历史、四份成绩单要维护。成本先付，收益要等「不知道该找谁」
  真的发生。一个人用的工具，四个角色的边界他本来就清楚。
* **BOT 之间自己协调、权限给高。** 明确不要。这套系统里最现实的事故形状就是
  「A 被日限额挡了，让 B 换个渠道发」—— AGENTS.md 已经点名的那一条。代价是一个
  带着微信和全部客户的 WhatsApp 号。角色之间只通过提议队列传话，不互相直接执行。
* **让命令改代码或改规格。** docs/86 是「产品能改自己」，但走的是先写编号规格、
  再加失败测试、再实现。一句话直接改配置没有那道门。


## 实现之后补记（09-02）

写规格时把「安全拦下 14」和「质量延后 6」当成了可以争取回来的量，查了才知道不是：

```
delay   上一封是 2026-09-01，同渠道 14 天内不再发   ×6
```

拦下的 14 条走的是 `message_guard`，三条规则之一：文本里出现价格、出现退出语、
首封没有可识别的个性化线索。两类都不是开关，是「昨天刚发过」和「这封信写坏了」。
09-02 当天两次提交（`5ab3e91`、`e9f4385`）把 hook 写进了正文，那 14 条重跑守卫全部通过 ——
**修法是改文案，不是给守卫开口子。**

同一次核对里另外两个数字也被推翻，记在这里免得下次又当成机会：

* 「526 家可发」是错的。`outreach.never_touched('email')` 真实只有 **3** 家；
  831 家没进过 `send_log` 的公司里，506 家在 `outreach` 上带着 2022–2026 的
  `message_sent_date` —— 是小满导入的历史联系人，排除它们是对的。
* 真正的池子是 `recontact.reapproachable` 的 **498** 家，而 `autosend._top_up`
  早就每天从这里取。**瓶颈不是池子，是邮箱日额度（当前单个邮箱 60 封/天）。**
