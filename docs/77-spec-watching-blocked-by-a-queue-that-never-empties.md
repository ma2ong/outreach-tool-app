＃ 77 — 关注从来没发生过，因为队列永远不空

## 现象

Allen 在 thorav.us（#987）的页面上看到私信和关注一直卡着。查库确认，比"卡着"更糟：

```
social_watch_date        = <缺失>
social_watch_count       = <缺失>
social_follow_count      = <缺失>
```

这三个键从来没被写过。也就是说 [71 号](71-spec-social-watching.md) 的浏览、
[72 号](72-spec-social-outreach.md) 的关注，**上线以来一次都没有执行过**。不是慢，是零。

## 原因

[71 号 R2](71-spec-social-watching.md) 写的是：

> **当天还有待发私信时，不做浏览。**

代码照着实现了：

```python
def sending_pending(conn) -> int:
    return conn.execute(
        "SELECT COUNT(*) FROM social_dm_queue WHERE queue_date=? AND status='ready'", ...)
```

而 [52 号](52-spec-social-dm-daily-queue.md) 的队列**在设计上就不会被清空**：

- 每天早上重建 20–30 条（今天 28 条：instagram 15、whatsapp 8、facebook 5）
- `auto` 渠道每轮最多发 1 条，且只发"此刻正好到点"的那条，错过 2 小时就永远跳过
- `manual` 渠道的行根本不会被自动发走，它们就是留给 Allen 按的

所以 `sending_pending` 一天里**几乎不可能归零**。`watch()` 每轮都在第一行掉头就走，
关注额度一次都没花过。

`main.py` 里 `run_due()` 和 `watch()` 还是同一个函数里前后脚调用的，
更保证了 watch 看到的永远是一个刚建好的满队列。

## 这里改的是规则，不是绕过规则

R2 那句话自己写清楚了真正的理由：

> 同一个账号在**同一分钟**里既在发私信又在浏览陌生主页，是最像机器的行为模式。

危险的是**时间上的重合**，"当天还有待发私信"只是当时随手选的一个代理指标——
而这个代理指标永远为真，于是把一条"错开时间"的规则变成了一条"永不执行"的规则。

## R1 用真的发送时刻挡，不用队列长度挡

浏览的前提从「今天队列空了」改成：

> **最近 20 分钟内没有真的发出过任何一条社媒私信。**

判据是 `social_last_send_at_<渠道>`——那是真正发出去的那一刻，不是排队的意图。
20 分钟是因为操作循环 15 分钟一轮：任何真的发过信的那一轮都会被跳过，
下一轮才轮到浏览。

这条比原来的规则**更贴近 R2 想防的事**：原来的规则里，一条排在下午四点的私信
会挡住上午十点的浏览；新规则不会，但真的在四点发了信，四点那一轮就不浏览。

## R2 71 号 R2 和它的验收条目 2 作废

原文：「当天还有待发私信时，一个主页都不看」→ 改为「刚发过私信的那一轮不看主页」。
其余限制（每天 20 个、间隔 40–90 秒、失败不重试、不点赞不评论）**一条都不动**。

## R3 晨报不再把这件事说成是故意的

`morning_readout` 现在会说「社媒主页一个没看：今天还有 28 条私信没发完（**这是刻意的**）」。
它每天都在把一个 bug 汇报成一个设计。零浏览连着出现，该说的是这不正常。

## 验收

1. 队列里有 28 条 `ready`、但最近 20 分钟没发过信 → 浏览照常进行
2. 刚发出一条 instagram 私信 → 这一轮不浏览
3. 20 分钟后的下一轮 → 恢复浏览
4. 每天 20 个上限、40–90 秒间隔、关注 10 个上限：全部不变
5. 晨报里零浏览不再被描述成刻意
