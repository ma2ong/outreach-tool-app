# Doc 15 — 全系统审计：成交执行与触达安全

**状态：** Approved / Implementing  
**审计日期：** 2026-08-04  
**范围：** doc 10–14、前后端实现、376 个后端测试、生产构建、真实 `outreach.db`

## 1. 结论

系统的“找客户 → 验证 → 触达 → 回复识别”主链已经能真实运行，但还存在两个会直接伤害销售结果的偏差：

1. **已读不等于已处理。** 真人回复打开后未必已经回复、建商机或安排下一步，但当前未读徽章会消失。真实库中唯一一条真人回复已经读过，同时客户没有下一步动作、跟进日期或商机，存在丢询盘风险。
2. **多渠道同日轰炸。** “一键全渠道”会让同一客户在 Email、WhatsApp、Instagram、Facebook 同时收到相似内容。各渠道独立限额不能解决品牌骚扰问题；专业销售系统需要跨渠道联系频率上限。

此外还有两个可靠性偏差：历史退信仍占用收件箱未读数；SQLite 在回复轮询、自动发送和 API 同时写入时没有等待/并发保护。

## 2. 真实数据审计

- 客户 920 家：已联系 610、新客户 309、已回复 1。
- 活跃邮件序列 315 条，最早到期 2026-07-14；自动发送已启用，2026-08-04 成功发送 30 条。
- 邮箱 562 个，已检查 539 个，其中无效 32 个。
- 联系人姓名 73 个、职位 28 个、ICP 分级 219 个。
- 收件箱：历史退信 17、Instagram 自动回复 7、附件 4、真人回复 1。
- 下一步动作 0、跟进日期 0、商机 0、跟进备注 6。

判断：系统已解决“发不出去”，下一阶段的核心不是继续增加发送量，而是确保回复不丢、触达不过度、每个有效客户都有下一步。

## 3. 与产品设计的偏差

| 级别 | 偏差 | 用户影响 | 本轮处理 |
|---|---|---|---|
| P0 | 收件箱只有 `is_read`，没有“待处理/已处理” | 看过但未跟进的回复从首页消失 | 增加显式处理状态与待处理计数 |
| P0 | 历史 bounce 仍显示为未读回复 | 首页显示 17 个假待办，掩盖真人回复 | API 只展示可行动消息，保留底层审计记录 |
| P0 | 一键四渠道同时发送 | 同一客户同日被多次打扰，伤品牌并增封号风险 | 移除同发入口，后端增加跨渠道每日一次保护 |
| P1 | SQLite 无 busy timeout / WAL | 后台同步与发送并发时可能 `database is locked` | 增加等待和 WAL 模式 |
| P1 | 原备份是单文件复制 | WAL 模式下可能漏掉尚未 checkpoint 的最新成交数据 | 改用 SQLite 原生一致性备份 API |
| P1 | 首页“今日能发”忽略单批上限 | 显示数量高于实际可发送量 | 同时按日额度和单批上限计算 |
| P1 | 渠道状态加载失败被静默隐藏 | 用户误以为只是“未连接” | 显示真实错误并给重试方向 |

## 4. 本轮验收标准

1. 历史退信不出现在收件箱列表，也不计入首页待处理数。
2. 打开真人回复只改变“已读”；只有点击“完成处理”才清除待处理提醒。
3. 同一客户当天已有任一渠道成功触达后，其他自动/批量渠道不再发送。
4. 界面不再提供一键四渠道同发入口，并解释如何错峰触达。
5. 所有 SQLite 连接都有等待锁的能力，主库启用 WAL。
6. 后端全量测试、前端构建和浏览器冒烟全部通过。

## 5. 后续产品路线（不混入本轮修复）

### P0：销售活动 / 任务

下一版应把“下一步动作”升级为独立 Activity：电话、邮件、WhatsApp、会议、报价、截止日，并关联客户和商机。Pipedrive 与 EspoCRM 都把 Activity 作为推动成交的核心对象，而真实库当前 0 个下一步动作，说明仅靠客户字段不足以形成习惯。

### P1：公司与多联系人

920 家公司只有 73 个联系人姓名、28 个职位；需要一家公司多联系人、决策角色、语言、时区和首选渠道，避免把公司邮箱当决策人。

### P1：正式报价到订单

当前报价卡只是图片附件，未关联商机、版本、币种、贸易条款、LED 配置计算和收款/生产/出货节点。应按 doc 14 Wave Q 独立实施。

### P2：LED 购买信号与可解释评分

补展会、项目发布、招标、中标、招聘、经销品牌等带来源信号；只有可信信号可生成“为什么现在联系”，不自动发送。

## 6. 外部产品借鉴

- Pipedrive 将电话、会议、任务、邮件等 Activity 关联到人员、公司、Lead、Deal 或 Project，核心是明确“下一步是什么”。
- EspoCRM 在 Account、Contact、Lead、Opportunity 中统一提供 Activities 面板。
- Mautic 的 Frequency Rules 跨 Email、SMS 等渠道限制联系频率；本系统应采用更保守的“同一客户每天最多一次批量触达”。
- listmonk 对 hard bounce 一次即 blocklist，并把退信处理与普通收件箱分开；当前无效邮箱抑制方向正确，但历史展示需要清理。
