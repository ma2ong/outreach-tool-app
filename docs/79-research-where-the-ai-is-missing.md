＃ 79 — 调研：agentconnect 能借什么，以及这套系统的 AI 缺在哪

Allen 问了三件事：agentconnect 有什么可借鉴的（尤其 agent 的能动性）、要不要接一个
能对话改自己的界面、能不能接入更多 AI 能力。放在一起答，因为答案是同一个。

## 一、agentconnect：能借的比想象中少，但有一条值得抄

[agentconnect](https://github.com/agentconnect-md/agentconnect) 是「Claude Tag 的开源
多 agent 替代」：把多个 agent 托管起来，让它们和人一起出现在 Slack / Telegram / 飞书 /
GitHub 的同一个会话里。三层结构——daemon（跑 agent、管 workspace 和 session）、
relay（回调入口）、control plane（认证、权限、可观测性，且**只存协调元数据，不存消息正文**）。

**它解决的问题不是 Allen 的问题。** 它是给一个团队托管一群 agent 用的：角色化配置、
agent 之间互相调用、按仓库/工具/agent 划权限。这套系统是单人单业务，多 agent 编排
在这里是纯开销——`backend/app/agent/` 已经有 33 个模块，它们不是不够独立，是已经够多了。

**唯一值得抄的一条是它的交互形态：人和 agent 在同一个会话里，agent 的动作在会话里可见。**
这条正好是 Allen 问的第二件事，下面单独说。

顺带看了同类：[OpenSales](https://github.com/siddartha19/OpenSales)（VP/SDR/AE 三个 agent
加一个复核的 manager）、[b2b-sdr-agent-template](https://github.com/iPythoning/b2b-sdr-agent-template)
（10 阶段管道 + 4 引擎记忆 + WhatsApp/Telegram/邮件多渠道）。**它们有的东西这套系统
基本都有**，而且这套系统多了它们没有的：真实的额度和封号红线、按国家的自主开关、
可溯源的事实规则（docs/45）。不缺架构。

## 二、这套系统的 AI 到底用在哪——查完之后的结论

全仓库调用模型的地方只有四个：

| 模块 | 干什么 |
|---|---|
| `agent/classify.py` | 分类客户回复 |
| `agent/draft.py` | 起草回信 |
| `agent/memory.py` | 把往来总结成客户记忆 |
| `agent/plan.py` | 规划今天做什么 |

**四个全部发生在「已经联系上了」之后。** 而联系之前的每一个判断——这家公司是干什么的、
是不是买家、该不该关注、简介写什么——全是正则和关键词：

- `icp.py`：五类关键词的子串匹配
- `screening.py`：国家码、TLD、品牌名单
- `brief.py`：正则抽 P2.5 这样的箱体规格
- `social_watch.looks_like_a_customer`：简介里有没有 LED 相关词

**今天上午修的每一个 bug 都在这条线上**（docs/78）：真的 AV 集成商因为官网没写
"system integration" 被判成 unknown；一篇 naver 博客因为满屏 LED 关键词拿了高分；
一张 Cloudflare 反爬页被读成一家 85 分的集成商。这些不是关键词表没写全，是**用子串
匹配去做一个判断题**。

## 三、建议一：ICP 分类换成模型判断，简介和开场白不动

这两件事风险不是一个量级，而现在的代码用同一条规矩管着它们：

| | 读者 | 错了的代价 | 该用什么 |
|---|---|---|---|
| **ICP 类型和分数** | Allen 自己 | 一家客户排错序 | **模型判断** |
| **brief / hook** | 客户本人 | 一句编造的话进了信里，整封信从那句起就像机器写的 | **保持正则** |

`brief.py` 开头那段「不推断、不改写」的理由是对的，**但它只对 hook 成立**。
把同一条严格规矩套在内部标签上，换来的是 avidex 被判 unknown。

具体做法：把官网正文交给 DeepSeek（`llm.py` 里已经接好，而且 `classify` 这条道
本来就是为「高频、低难度、不能烧 Claude 额度」设计的），问三件事——
这家是做什么的、属于哪一类买家、判断依据是原文哪一句。**要求它引用原文**，
引不出来就返回 unknown，这样它和 docs/45 是一致的：写不出出处的不写。

成本：1300 家客户重跑一遍，DeepSeek 的价格下大概几块钱。

## 四、建议二：对话式界面做，但只做一半

Allen 想要的是「在系统里直接跟 agent 说话，让它改自己的界面或功能，不用每次来找你」。
这里面其实是两件事，值不值得做差得很远：

**值得做——跟 agent 谈生意。**
「把韩国的客户暂停一周」「给 DisplayHub 写封信，提上次那个 시공 项目」
「这周为什么一个回复都没有」。这些今天要么点五个页面，要么来找我。
所需的东西全都有了：`agent/world.py` 知道业务状态，`agent/plan.py` 会规划，
`agent/executors.py` 会执行，`agent/proposals.py` 有「提议→确认→执行」的闭环。
**缺的只是一个输入框**——把话变成一条 proposal，然后走现有的确认和执行路径。
风险可控，因为所有危险动作（发信、关注）本来就压在既有的额度和自主开关下面。

**不值得做——让它改自己的代码。**
三个理由，按分量排：

1. **它改的是正在给客户发邮件的那个进程。** 一次坏改动的代价不是页面白屏，
   是当天的信发错人或者根本没发出去，而这类失败今天上午已经见过一次了
   （docs/77：关注功能静默地一次都没跑过，没有任何报错）。
2. **改代码这件事需要的东西，一个输入框给不了**：跑测试、看 diff、回滚、
   1395 个测试的回归网。这些正是 Claude Code 已经在做的事，在 app 里重做一遍
   只会做出一个更差的版本。
3. **界面改动的瓶颈从来不是「找我」这一步**。今天上午这些改动，慢的部分是查清楚
   「关注为什么没跑」和「hook 为什么全丢了」，不是敲键盘。

**折中方案：让 agent 能提「功能建议」，但产物是一句需求，不是一段代码。**
他在框里说「客户页太乱」，agent 记成一条待办、写清楚它理解的问题，
下次开 Claude Code 时这条就在那儿等着。省掉的是「他想到但忘了说」的损耗，
那个损耗是真的。

## 五、优先级

1. **ICP 换模型判断**（第三节）——直接修今天发现的那一类失败，成本几块钱，风险只在内部标签
2. **对话框：跟 agent 谈生意**（第四节上半）——所有零件都在，缺一个入口
3. **功能建议记成待办**（第四节下半）——小，且能立刻减少「忘了说」
4. 多 agent 编排、自改代码 —— **不做**，理由见第一节和第四节

## 不做的事

- 不引入 agentconnect 本身。它要 daemon + relay + control plane 三层，
  为了一个单人系统跑三个服务，换来的是本来就不需要的多 agent 权限模型。
- 不把 brief/hook 交给模型。理由是 `brief.py` 开头那段，它没有过期。
